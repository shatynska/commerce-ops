Tests come from the delta specs, not from the code: per `AGENTS.md`, `openspec-test-writer` is dispatched after this change's specs are approved and **before section 1 begins** — before any implementation, section 1 included. Section 1 has the widest blast radius in this change and its tasks read the suite's failures, so deriving its tests afterwards would shape them to the code that already exists, which is precisely how all four of these defects passed review the first time. Section 6 records what the derivation produced and what had to be corrected in tests that pin today's defects; only 6.4-6.5's corrections to existing tests follow implementation, because they are corrections rather than derivations.

## 3. Roster-backed mention resolution

- [ ] 3.1 Give `resolve_mention_target` (`launch/application/thread_establishment.py`) a keyword-only `roster: RosterReader | None` and resolve a step's `confirmer` through it: read `list_people()`, match on `person_identifier(person)` — the same pair `automated_decisions.py:194` matches on, so the mention and the decision check can never disagree about who the confirmer is — and return that person's `slack_identity`. Import `RosterReader` and `person_identifier` from `launch/application/playbook_authoring.py`, where both are already public.
- [ ] 3.2 Treat a confirmer as resolvable for tagging only where the roster carries them, carries a `slack_identity`, **and** carries them active. The active check is the one that matters: `roster` keeps a deactivated entry's Slack identity intact, `launch-step-automation`:225 accepts a decision only from an active confirmer, and `playbook-authoring`:145-146 guarantees such a step keeps being served with its results held pending — so a deactivated confirmer is reachable, durable, and must not be tagged for a decision that cannot be accepted from them.
- [ ] 3.3 Keep the return type `str | None`. Neither a richer result nor a policy parameter is needed: each caller already holds `step`, so "a named confirmer that could not be resolved" is `step.confirmer` set and the answer `None`, and a step naming no confirmer yields the submitter instead — the two can never be confused. Leaving the shape alone is also what keeps the gate ask and the launch confirmation genuinely untouched rather than edited mechanically.
- [ ] 3.4 Read the roster only on the confirmer branch. `launch.submitter` is already a Slack identity; returning it must not touch the reader, so the gate ask, the launch confirmation and every step naming no confirmer keep working through a roster outage or a missing injection.
- [ ] 3.5 Report every gap, naming the step, the launch and the unresolvable confirmer, mirroring `_clickup_users`'s two warnings. Keep the "carried without a Slack identity" branch as defence-in-depth and label it as such in a comment — `roster`:10 forbids that state and `Person.faults()` enforces it, so unlike the other two it is not a state the specifications say occurs.
- [ ] 3.6 Catch a reader that is absent, of the wrong shape (`UnreadableRosterError`) or failing; report it and resolve no identity. Deliberately the opposite disposition from `_roster_or_fail`, which raises — there the roster read *is* the decision, here it is an embellishment on a message whose substance does not depend on it.
- [ ] 3.7 Correct the docstring's claim about the return value, which is what this change makes true: a Slack identity usable in `<@…>` without further translation, or nothing.
- [ ] 3.8 In `automation_confirmation.deliver_pending_result`, drop the tag when `step.confirmer` is set and the resolved mention is `None` — do not substitute the submitter. In `automation_pass._report_stuck_step`, do the opposite on the same condition: tag `launch.submitter` and add a line to `_stuck_step_message` naming that the step's confirmer could not be resolved. Both functions already hold `step`, and `_report_stuck_step` already holds `launch`, so neither needs anything new to tell the cases apart. The two paths differ because only the ask is governed by `launch-step-automation`:225; each delta states its own reason, so implement them from those rather than by copying one to the other.
- [ ] 3.9 In `launch/infrastructure/driven/launch_thread_delivery.py`, add the injected `read_people` module global and pass it to `resolve_mention_target`. Module-level and injected, matching the seam every other roster consumer in `launch` uses and that its own docstring explains. Its `(thread_ts, mention)` return is unchanged, so `gate_confirmation.py` and `slack_entry.py` need no edit at all.
- [ ] 3.10 Wire it from both roots: `launch_thread_delivery.read_people = _RosterReader()` in `src/commerce_ops/main.py`, next to the existing assignments; `launch_thread_delivery.read_people = clickup_sync_job.read_people` in `src/commerce_ops/worker.py`, reusing the stateless reader as `gate_progression_job` already does. Both processes need it — the confirmation and the gate ask run in the HTTP process, the automation pass's two affected messages in the worker.
