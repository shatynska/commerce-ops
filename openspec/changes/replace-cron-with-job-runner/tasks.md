## 0. Prerequisites

- [ ] 0.1 Confirm `configure-application-logging` has landed — a worker's value is what it reports
- [ ] 0.2 Confirm `centralize-database-session` has landed — the worker needs a session outside any HTTP request, and its narrowed one-pool requirement is what makes the queue's own connection compatible

## 1. Dependency and schema

- [ ] 1.1 Add `procrastinate` to `pyproject.toml` with a pinned major (`>=3.9,<4`); run `uv sync` and confirm `psycopg[pool]` arrives with it. If the dependency footprint differs materially from design.md's account, report before proceeding
- [ ] 1.1a Tie the vendored schema (1.4a) to the installed runner version: add a test asserting the installed runner's schema version matches the one the migration vendored. `>=3.9,<4` permits a minor upgrade that ships schema migrations, and without this a routine `uv lock --upgrade` runs newer runner code against 3.9's tables — failing at runtime, in the window before `report-overdue-scheduled-runs` can report it
- [ ] 1.2 Derive the queue's `psycopg`-style connection string from `DATABASE_URL` rather than delivering a second secret — the deploy renders one URL, and `docker-compose.yml` constructs it from `POSTGRES_PASSWORD`
- [ ] 1.3 Add an Alembic migration installing the runner's schema, executing the multi-statement script through **asyncpg's own `Connection.execute()`** — reached from the raw driver connection under the bind (`op.get_bind().connection.driver_connection`; confirm the exact attribute path against the installed SQLAlchemy). Because the migration body runs synchronously inside `connection.run_sync(...)` (`alembic/env.py:80`), awaiting that coroutine needs the greenlet bridge, `sqlalchemy.util.await_only`.

  Do **not** use `op.execute` or `exec_driver_sql`: both are SQLAlchemy `Connection` methods that route through dialect execution and therefore through the same prepared-statement path that rejects multi-statement SQL — verified, `Connection.exec_driver_sql` goes through `_execute_context`. An explicit `$$`-aware statement split is the fallback, not the first attempt: it is the fragile branch (design.md — "Install the runner's schema through Alembic")
- [ ] 1.4 Give the migration a `downgrade` that drops the runner's schema. The runner ships no teardown script, so enumerate the object classes by hand: tables, sequences, enum types, functions and triggers. This is likely the second-largest body of SQL in the change — budget for it rather than treating it as one line
- [ ] 1.4a **Vendor the schema SQL into the migration** rather than reading it from the installed package at upgrade time. Reading it at upgrade time would make one revision produce different schemas depending on the installed runner version — the opposite of the version-pinning that justified using Alembic at all (design.md — "Install the runner's schema through Alembic")
- [ ] 1.5 Verify `uv run alembic upgrade head` then `uv run alembic downgrade -1` both succeed against a local Postgres. "No orphaned objects" needs a real check, not a glance at `\dt`: query `pg_class`, `pg_type` and `pg_proc` for the runner's prefix and require empty results after the downgrade — a missed function or enum type is invisible to a table listing. If the execution mechanism in 1.3 proves impractical, stop and report rather than silently falling back to the runner's own CLI
- [ ] 1.6 **Exclude the runner's tables from autogenerate.** `alembic/env.py` sets `target_metadata = Base.metadata` with no `include_object`/`include_name` filter, and `Base.metadata` describes `products`' models only — so once the runner's tables exist, the next `alembic revision --autogenerate` for any unrelated feature emits `op.drop_table` for each of them, destroying the run history. Add a filter rejecting the runner's table prefix (design.md — "a hazard that neither branch avoids")
- [ ] 1.6a Put the filter predicate in an **importable module** under `src/commerce_ops/shared/infrastructure/driven/`, not in `alembic/env.py` — that file has no `__init__.py` beside it, a top-level `alembic` package would shadow the installed distribution, and its module body calls `context.config` at import, so a predicate defined there cannot be unit-tested. `env.py:10` already imports from `commerce_ops`, so the precedent exists
- [ ] 1.6b Pass the filter at **both** `context.configure()` calls in `alembic/env.py` — the offline path (line 49) and the online path (line 61) — so the two cannot diverge
- [ ] 1.7 Test the filter: assert it rejects the runner's table names and accepts a `products` table, so deleting it fails rather than silently re-arming the hazard
- [ ] 1.8 Confirm empirically: with the runner's schema applied, run `uv run alembic revision --autogenerate` against a local Postgres and check the generated migration contains **no** `drop_table` for a runner table. Discard the generated file

## 2. Runner, job definitions and worker

- [ ] 2.1 Add the runner's application object in `shared/infrastructure/driven/`, configured lazily so importing it requires no `DATABASE_URL` (consistent with `runtime-configuration`'s import/start requirement)
- [ ] 2.2 Add the daily digest job in **`products/infrastructure/driving/`** — a scheduled job is a driving adapter, and this placement lets it reach `products`' own repository and notifier without `shared` ever importing a business module (design.md — "The daily job definition lives in `products`")
- [ ] 2.3 The job calls the existing `run_daily_digest` use case through `centralize-database-session`'s `session()` context manager and `ProductRepository`, with **no change to the use case itself**
- [ ] 2.4 Declare the daily schedule (06:00, matching today's crontab). Determine whether the runner accepts a per-job timezone: if it does, declare it in the job definition as the single source of truth for when work is due; if it interprets schedules in UTC regardless, **stop and report**: the requirement's "explicitly configured timezone" wording is what needs revisiting, not the test. Do not weaken test 5.1 to fit. Either way `TZ` on the container is for log timestamps, not for scheduling (design.md — "`TZ` is set explicitly to UTC")
- [ ] 2.5 Establish the missed-window behavior and record the mechanism, rather than assuming it: determine whether the runner performs a missed window once on return by default or requires configuration, name the knob or the default in design.md, and confirm by test (5.4, 5.5) that several missed moments produce one run — not a replayed backlog (spec: "A Window Missed While No Worker Was Available Is Run Once On Return"). If it turns out neither configurable nor defaulted this way, stop and report: the requirement, not the implementation, is what would need revisiting
- [ ] 2.6 Configure the daily job's retry strategy: exponential backoff, small maximum attempts. Initial figures to record and revisit: 3 attempts, 60s base
- [ ] 2.7 Ensure a Slack delivery failure neither fails the run nor triggers a retry, while a database read failure does both (`product-monitoring` delta)
- [ ] 2.7a Post the database-read failure message **only on the attempt the retry strategy will not retry** — read the attempt number from the runner's job context and the maximum from the single place task 2.6 declares it, so the two cannot drift apart. Without this, one outage posts one message per attempt, which is what the delta's "An intermediate failed attempt does not post" scenario forbids (design.md — "Retries")
- [ ] 2.8 Add the worker entry point (`src/commerce_ops/worker.py`, beside `main.py` and `preflight.py`, outside the `.importlinter` containers), calling `configure_logging()` first, **importing the job definition modules so their schedules are actually registered**, and disposing the session provider's engine on shutdown. A worker that registers nothing runs healthy and schedules nothing — and with the healthcheck disabled by task 3.3, nothing would show it
- [ ] 2.8a Run `preflight` in the worker's command chain, as `app`'s chain does. Its `command:` override otherwise drops that step, so a missing `PRODUCT_AGENT_MONITORING_CHANNEL_ID` would surface as a failed 06:00 job rather than a named report at container start. Running it also keeps `deploy-pipeline`'s configuration-check requirement unambiguous now that two containers run from one image, without needing a delta to rescope it
- [ ] 2.8b Apply the same `exec` requirement to the worker's command that `centralize-database-session` applies to `app`'s: without it `sh` stays PID 1, SIGTERM never reaches the worker, and its engine disposal and in-flight job handling never run
- [ ] 2.9 Do **not** declare schedules for the weekly, biweekly, monthly or quarterly cadences; leave `run_pending_cadence_report` in place, unscheduled and uncalled
- [ ] 2.10 **First confirm the runner's history carries, per run, which work it was, when it started, when it ended, and its outcome** — the `scheduled-jobs` requirement demands all four and the accessor is raw SQL over the physical tables. If the history does not carry them in that shape, stop and report: the requirement is what needs revisiting, not the query. Then add a last-success accessor in `shared/infrastructure/driven/`, over the runner's job history, returning the time of a piece of work's most recent successful run or a distinct never-succeeded result. This change specifies and tests that behavior (`scheduled-jobs`: "The most recent successful run can be identified"; test 5.9) and `proposal.md` claims queryability as its own deliverable, so it must be implemented here — `report-overdue-scheduled-runs` consumes it rather than building it
- [ ] 2.10a Have the accessor query through `centralize-database-session`'s session provider, **not** through the runner's own connector. The sibling's freshness endpoint calls it from the HTTP process, which otherwise acquires the queue's second pool for a read that is not queue work — widening the two-driver footprint design.md scopes to the worker
- [ ] 2.11 Move `_format_daily_message` and `_attempt_post` from `monitoring.py` into the daily job definition **unchanged** — they produce the digest's actual Slack text, and task 4.1 permits deleting the module they currently live in

## 3. Compose and deploy

- [ ] 3.1 Remove the `cron` service and the `app_cron` network from `docker-compose.yml` — **including `app`'s own `networks:` entry for `app_cron`**, which is a separate line from the network definition and whose omission leaves a stack that will not start
- [ ] 3.2 Add the `worker` service: same `image:` and `env_file:` as `app`, `command:` overridden to run the worker, networks `app_db` only, `restart: unless-stopped`
- [ ] 3.3 **Override the image's healthcheck on `worker`** with `healthcheck: disable: true` — the `Dockerfile`'s `HEALTHCHECK` polls `http://localhost:8000/health`, which the worker does not serve, so it would report unhealthy forever (design.md — "with the healthcheck overridden")
- [ ] 3.4 Give `worker` **both** `depends_on` conditions: `postgres: condition: service_healthy` and `app: condition: service_healthy`. The second is schema readiness, not HTTP coupling — `app` becomes healthy only after its `alembic upgrade head` completes, which is what stops the worker crash-looping against a database with no runner schema on first deploy
- [ ] 3.5 Give `worker` the same `DATABASE_URL` construction `app` has, so one secret still backs both
- [ ] 3.6 Set `TZ=UTC` explicitly on both `app` and `worker`
- [ ] 3.6a Do **not** declare `TZ` in the settings model. The runtime does not require it: the schedule's timezone lives in code (task 2.4), a container with no `TZ` already runs UTC, so `TZ=UTC` records the decision and shifts nothing — the application behaves identically without it. design.md's `TZ` decision records this, so no `Settings` field, no `ENV_VAR_EXEMPTIONS` entry, and no amendment to `test_settings.py`'s transcriptions is needed
- [ ] 3.7 Remove `TRIGGER_SECRET` from `.github/workflows/deploy.yml`'s `.env` render step
