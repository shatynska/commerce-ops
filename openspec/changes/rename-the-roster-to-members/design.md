## Context

See `proposal.md` — *Why*. The state that shapes the approach:

- **~4,800 occurrences across 144 files**, of which ~3,900 are in 93 test
  files. A rename at that scale is not reviewable as 4,800 individual edits,
  and it is not reliably performed as 4,800 individual edits either.
- **No behaviour changes**, so the whole change is judged on one question:
  *is the substitution faithful and complete?* Everything below exists to
  make that question machine-answerable rather than a matter of a reviewer's
  stamina.
- **The change declares no specification deltas** (`skip_specs: true`), so it
  owes no new tests and the existing suite is the completion gate. The
  reasoning and the alternative are in `proposal.md` — *Capabilities*.
- **`import-linter` holds `access/application/__init__.py` as the module's
  only public surface.** Every consumer imports through it, so the rename
  cannot leak a private path by accident: a missed site fails the contract
  check rather than merely the type check.

## Goals / Non-Goals

**Goals:**

- One vocabulary for the people directory, in code, database, specs and UI.
- A rename that is **generated and diffed**, not hand-typed and reviewed by
  eye — so the review question is "is the map right?" (a table of ~50 rows)
  rather than "did 4,800 edits stay faithful?" (unanswerable).
- A clean base for `rebuild-the-member-directory`, whose diff then contains
  no rename noise at all.

**Non-Goals:**

- **Roles.** No role concept, table, seed or page. That is
  `rebuild-the-member-directory`.
- **The page rebuild.** `team.html` is `roster.html` with its words changed —
  the *Add a person* form stays at the top of the page, the `actions` column
  keeps its two inline `<form>`s, and `td.actions form { display: contents }`
  stays. Every one of those is a defect, and every one is
  `rebuild-the-member-directory`'s to fix. Fixing them here would put a
  behaviour change inside the change whose entire warrant is that it has
  none.
- **`Person` as a general English word.** `person` is renamed where it names
  *this* concept. Prose that says "a person" about a human in general —
  `admin-session`'s *"the person who minted the link"* — is not this
  directory's entity and is left alone. The map is applied to identifiers
  mechanically and to prose deliberately; this is the boundary between the
  two.
- **Reclaiming the word `member` from its other senses.** `proposal.md`
  rejected `collaborator` because 26 existing uses already mean a supplied
  port. That test was not applied to `member`, and it does not come back
  clean: the shipped specs already use it for set membership
  (`shared-vocabulary:40,127,130`), enum membership
  (`launch-admin:892,894,969,972`), network membership
  (`deploy-pipeline:106`) and Slack **workspace** membership
  (`slack-trigger:47,51,52,55,56` — deliberately *not* this directory). The
  map never rewrites an existing `member`, so nothing breaks; what is at risk
  is prose clarity. Sharpest case: `access-scope`'s *"An active member
  resolves to the unrestricted scope"* sits one capability away from
  `shared-vocabulary`'s *"an explicit-set scope permits exactly its
  members"*, where the members are products. The hand pass therefore **keeps
  a qualifier wherever the sense is ambiguous** — *"a member of the
  directory"* rather than a bare *"a member"* — instead of dropping every
  qualifier because the program plan says one can be dropped.
- **Squashing or editing the 28 applied Alembic revisions.** Change 9 of the
  program does that, deliberately last.

## Decisions

### 1. The rename is generated by a committed script, not hand-typed

A script carrying the substitution table is committed in the change
directory, applied to the tree in one pass, and its output is the commit.
Verification is then a property of the process rather than a claim about it:

```
   pre-rename tree ──[ rename.py ]──▶ candidate ──diff──▶ committed rename
                                          │
                                          └─▶ must be empty for every file
                                              except the prose exceptions
                                              listed in section 5
```

**The input set is the whole tree minus a declared exclusion list**, and the
exclusion list is the *only* place the scope is decided. Nothing is renamed
by hand outside it — the `launch` seams, the ten driving adapters, the two
composition roots, the templates, the specs and the docs are all script
output, so the faithfulness check in section 8 covers them rather than
stopping at whatever subtrees a task list happened to name. The exclusions:

| Excluded | Why |
|---|---|
| `openspec/changes/**` | The archives are history (§7). **This change's own directory is inside it** — its artifacts quote the pre-rename vocabulary as the evidence for renaming it, and a directory named `rename-the-roster-to-members` cannot survive its own substitution. |
| `alembic/versions/**` | Applied revisions; their identifiers are what deployed databases hold (§4). |
| `.git/`, `.venv/`, `uv.lock` | Not source. |

**Alternative considered — hand-edit and review the diff.** Rejected on
arithmetic. A reviewer confirming 4,800 hand edits is confirming a negative,
across 144 files, in one sitting. A reviewer confirming a 50-row table plus
an empty diff is confirming something a person can actually hold. The script
also makes the change re-runnable, which matters because it will be rebased
under `share-the-unit-test-harness`.

**Alternative considered — a single global stem substitution.** Rejected: the
map is not one stem rule (section 2), and a blind global would produce
`members_members`, `MembersMember` and `ALICE_MEMBERS_ID`.

### 2. The map is a table, ordered longest-match-first, not two stem rules

`roster` does not map to one word. It is the collection in `Roster`, the
singular possessive in `ALICE_ROSTER_ID` ("Alice's roster identifier" →
"Alice's member identifier"), and it disappears entirely in `roster_people`
(the table becomes `members`, not `members_members`). The rows that carry
judgement rather than mechanism:

| From | To | Why not the obvious thing |
|---|---|---|
| `Roster` | `Members` | The validated collection. `Members(members=…)` reads oddly in its own constructor but never collides with the plural of the entity, which `Member`s would. |
| `Person` | `Member` | The directory's inhabitant. |
| `RosterPerson` | `MemberRow` | **Not** `Member` — the ORM row and the domain value are different things in different layers, and the existing name already distinguishes them by prefix. Collapsing them would make `models.py`'s import shadow the domain entity. |
| `RosterSet` | `MembersSet` | Follows `Members`, and mirrors `playbook_step_set` / `PlaybookStepSet`. |
| `roster_people` | `members` | The table names the collection, not "rows of members". |
| `roster_set` | `members_set` | Consistent with `MembersSet`. |
| `ALICE_ROSTER_ID` | `ALICE_MEMBER_ID` | Singular: it is one person's identifier, not the collection's. Same for the other six `*_ROSTER_ID` test constants. |
| `list_people` | `list_members` | `people` is this concept's plural here, not English's. |
| `read_roster` | `read_members` | Reads the collection. |
| `_FakeRosterStore` | `_FakeMembersStore` | Follows `MembersStore`, not `Members`. |

**The admin surface renames to `team`, not to `members`, and needs its own
rows.** `roster → members` cannot produce any of it. Without these rows the
script emits `/admin/members` and `members.html`, and check 1 then reports
differences on identifier lines with no row to add and no precedence rule for
adding one:

| From | To | Note |
|---|---|---|
| `/admin/roster` | `/admin/team` | Longer than `roster`, so longest-first already orders it ahead. |
| `roster.html` | `team.html` | Likewise. |
| `("roster", "/admin/roster", "Users")` | `("team", "/admin/team", "Team")` | The header row **whole**, so the key, path and label move together and cannot half-apply. Matching the tuple rather than its parts is also what keeps the label out of the map: `Users` alone is not a row. |

These three are substitution rows, not a hand-edited exception under §5: §5's
exception is scoped to non-identifier lines, and a route, a template filename
and a header key are all identifiers. Keeping them as rows keeps the surface
inside check 1, which is where everything belongs.

**There is deliberately no `Users → Team` row.** It was considered and
rejected on measurement: `Users` occurs seven times outside the exclusions,
and only two are the edit — `roster.html`'s `<title>` and `<h1>`. The other
five are text *about* the label, which the row would corrupt: the comment at
`_admin_header.html:39` explaining why the label reads *Users*, the statement
at `docs/playbook-program.md:381` that the `<h1>` "already reads *Users*",
the tuple at `_admin_header.html:45` (already covered whole by the row
above), and two test comments at
`test_roster_header_names_every_surface.py:124` and
`test_roster_admin_presentation_vocabulary.py:173` explaining an assertion
keyed on **lowercase** `"user"/"users"` that no row touches — so the row
would rewrite the comment to say *Team* while leaving the assertion keyed on
a word the surface no longer uses.

Three of those five are recoverable by hand and two are not worth the risk.
More to the point, `Users` is not a token class at all: it is **two display
strings in one template**, which is exactly §5's territory, and it is the
sole reason `tasks.md` 1.4's enumeration would have had to look past the two
stems. Without it, every substitution row carries a `roster` or `person`
stem and the two-stem enumeration is sound on its own terms.

The full table lives in the script. Rows are applied longest-first so
`roster_people` is consumed before `roster`, and `/admin/roster` before both.

**The table has a third row kind: `preserve`.** Some text carries the old
vocabulary *because it is about the rename*, and rewriting it destroys the
thing it records. A map with only `From → To` rows has no way to say so, and
would silently corrupt the two documents that explain why this directory
exists. `preserve` rows are matched first, ahead of every substitution:

Rows are keyed by **their text**, never by a line number: this change edits
`docs/playbook-program.md` (task 7.5), which shifts every line below the
edit before the map runs. Line numbers below are locators for a reader, not
match keys.

**Most preserve rows are derived, not enumerated.** An enumeration asserted
complete is only as good as whoever wrote it, and this one was found short
twice while being asserted complete both times. The class that caused both
misses has a rule:

> A token **names something inside an exclusion** when it resolves to a
> change directory under `openspec/changes/**` (written as a path, as a bare
> name, or as an archived name's date-prefixed form) or to a file under
> `alembic/versions/**`. Such a token earns **map protection** where it
> occurs outside the exclusions *when the map runs*, and **check-2
> permission** where it occurs outside them *in the committed tree*.

That is machine-checkable: the script lists those two directories and asks
whether the token resolves. It would have caught the five test-module
citations on the first pass without anyone having thought of test
docstrings, which is the property an enumeration does not have.

**The two conditions are separate because a preserve row does two jobs, and
they are earned at different moments.** Evaluated as one clause, the rule
misses its own third row: when the script is written, `rename-the-roster-to-members`
occurs *only* inside its own excluded directory, so a single "occurs outside"
test yields two rows — and then tasks 7.5 and 7.6 write the name into two
docs and check 2 reports correct text as a defect, which is the failure this
whole mechanism exists to prevent. Split by time, all four cases fall out
with no special case at all:

| Token | Map protection | Check-2 permission |
|---|---|---|
| `openspec/changes/move-principals-to-roster/` | yes | yes |
| `move-principals-to-roster` | yes | yes |
| `rename-the-roster-to-members` | **no** — the map cannot corrupt text that does not yet exist outside the exclusion | **yes** — 7.5 and 7.6 put it there |
| `a3d7e9f2c481_add_roster_tables` | no | no |

So the rule yields **two derived protection rows** and **three derived
permitted tokens**, and the alembic filename falls out of both columns rather
than by a stated exception.

The two enumerated prose rows below are protected too — they must be, or the
map destroys `docs/playbook-program.md:151` and `:153` — so the **finished
table carries four protection rows and five permitted tokens**. Stated here
as totals rather than left to be composed from two sections, because a
falsification condition written against a subtotal fires as a false alarm and
teaches an implementer that the condition is unreliable.

**Derived by that rule** — listed as documentation of what it yields, not as
the source of truth:

| Preserved | What breaks without it |
|---|---|
| The path prefix `openspec/changes/move-principals-to-roster/` | **A prefix, not the bare name.** Five test modules cite the delta spec they were derived from by full path, and two of those tails carry the word: `tests/unit/access/application/test_roster_bootstrap.py:4` and `test_roster_writes.py` cite `…/specs/roster/spec.md`, and `tests/unit/access/infrastructure/driving/test_roster_admin_page.py:6` cites `…/specs/roster-admin/spec.md`. Preserving only the change's name leaves those tails as ordinary tokens, rewriting them into `…/specs/members/spec.md` — a file that does not exist, since §7 keeps the archive's own directory names. The word is gone, so check 2 *passes*, and the test-to-spec traceability `AGENTS.md`'s test-design rule rests on is silently broken. |
| The bare token `move-principals-to-roster` | The archived change's name in prose: **20 occurrences across 20 files** outside `openspec/changes/**` — `AGENTS.md`'s Architecture summary, `docs/playbook-program.md:383`, `openspec/specs/access-scope/spec.md`, `src/commerce_ops/main.py:91`, `.github/workflows/deploy.yml:178`, four `access` source files and ten test modules. Rewritten, all of them reference a change that never existed. That `.github/workflows/deploy.yml` is named by no task is the clearest argument for §1's whole-tree input set. |
| `rename-the-roster-to-members` | **This change's own name.** Tasks 7.5 and 7.6 must write it into `docs/playbook-program.md` and `docs/proposed-change-order.md` — a pointer that does not name the change is not a pointer — and both files are outside the exclusions. Without this row the map rewrites the name into nonsense, and check 2 then reports correct text as a defect, in the same breath as §8 forbids relaxing the gate. |

`rename-the-roster-to-members` is listed above because it earns check-2
permission; it takes no map-protection row, since at map time it exists only
inside its own excluded directory.

The rule deliberately yields **neither** column for
`a3d7e9f2c481_add_roster_tables`. It occurs only under `alembic/versions/**`,
so the exclusion already protects it and a protection row would protect
nothing — while a permission row would fail check 2's symmetric half on a
correct tree, since it could never produce a hit in the searched region. §4
already records that the applied revisions keep their names; that is where
the guarantee lives.

**Enumerated residue** — prose quoting a prior state, which no rule can
derive:

| Preserved | What breaks without it |
|---|---|
| *"An active roster member resolves to the unrestricted scope"* and its two neighbouring quotations (`docs/playbook-program.md:153`) | They quote the **pre-rename** specs, and they are the evidence for the rename. Rewriting them makes the argument circular. |
| *"The people directory is `members`, not `roster`"* (`docs/playbook-program.md:151`) | Becomes *"is `members`, not `members`"* — an argument that destroys itself. |

This extends §7's principle from "the archive directory" to its actual
scope: **any text naming the old vocabulary because it is about the
vocabulary, rather than using it.** For the path-shaped tokens that scope is
mechanical, which is what the rule above exploits. For the two quotations it
is not — they are prose quoting a prior state, and nothing resolves them —
which is why those two alone stay enumerated.

The same files also contain ordinary `roster` uses
(`docs/playbook-program.md:212, 318, 389, 426`) that must be rewritten
normally, which is why the preservation is token-level: a file-level
exclusion would get those wrong in the other direction.

The `preserve` rows are also what keeps `tasks.md` §1.6's injectivity
assertion meaningful: a preserved token is never a substitution target, so it
cannot collide with one.

### 3. `principals.py` and `roster.py` are renamed too

`access/domain/principals.py` survived `move-principals-to-roster`, which
renamed the concept and not the file; its own docstring already opens *"The
roster: who is known"*. Leaving it would mean shipping a module named for a
vocabulary two renames stale. It becomes `access/domain/members.py`, and
`access/application/roster.py` becomes `access/application/members.py`.

That leaves two modules named `members.py` in one package, at different
layers. Accepted: they are disambiguated by their fully-qualified names
(`access.domain.members` / `access.application.members`), the repository
already carries `access/…/driven/models.py` beside
`launch/…/driven/models.py`, and the alternative — inventing a second word
for one of the two layers — is how the `principals`/`roster` drift started.

**Alternative considered — leave both file names alone.** Rejected: it keeps
the exact defect this change exists to remove, in the one file where it is
most misleading.

### 4. The database rename is `ALTER … RENAME`, not drop-and-recreate

`docs/playbook-program.md` licenses dropping tables — production data is test
data. This change declines the licence: renaming the two tables is three
statements, exactly reversible, and reads in the migration as what it is.
Dropping and recreating would be a larger, less reversible operation
performing a rename, and would make this the one change in the program that
destroys data without needing to.

One revision on `c04d95ba6e31`, the current single head. The 28 existing
revisions are applied history and keep their names —
`a3d7e9f2c481_add_roster_tables.py` still describes what it did.

### 5. Prose is corrected by hand, and the correction is bounded and listed

The mechanical pass produces *"an active members member"* from *"an active
roster member"*. Prose collapses like that are not invertible, so they are
not part of the machine-checked half. They are:

- **Bounded**: they occur only in spec prose, docstrings, comments and
  user-visible message strings — never in an identifier.
- **Enumerated where they are not prose collapses.** Two display strings are
  hand-edited rather than mapped: `roster.html`'s `<title>Users</title>` and
  `<h1>Users</h1>` become *Team*. They are here rather than in §2 because a
  `Users → Team` row corrupts five sites to fix these two (§2), and because
  `<h1>Users</h1>` carries no identifier, so §5's boundary test passes on it
  cleanly. Two further comments are hand-corrected alongside them: the one at
  `_admin_header.html:39` explaining why the label reads *Users*, and
  `docs/playbook-program.md:381`'s statement that the `<h1>` "already reads
  *Users*" — the latter absorbed by task 7.5's rewrite of lines 378–382.
- **Checked by construction**: after the hand pass, the difference between
  the script's output and the commit must touch **no line containing an
  identifier**. A difference on such a line means the map is wrong and the
  map gets fixed, not the file.
- **Reviewed as a diff.** The specs' own diff shows exactly the words that
  changed, which is what `proposal.md` — *Capabilities* argues is a better
  artifact than 40 restated requirement blocks.

The user-visible message strings are the ones to read closely, since several
are asserted in tests: `use_cases.py`'s *"the roster could not be read…"*,
`gate_confirmation.py`'s *"we can't read the roster right now"*, and
`clickup_sync.py`'s and `playbook_admin.py`'s *"whom the roster does not
carry"*. These become member-directory wording; no assertion is relaxed, only
its expected string renamed alongside the source.

**The noun the spec prose uses for the surface is *the Team page*.** The
capability is `members-admin` and the page is titled *Team*, and without a
rule the mechanical output gives "the members page" — which would leave the
surface with two names, a milder version of the four-names problem
`proposal.md` opens with. *Team* wins because it is what an admin actually
sees: the `<h1>`, the header entry and the URL all say it. The capability
keeps `members` because it names **what is administered**, not the page — as
`playbook-admin` names the playbook it administers. That analogy establishes
the principle and not the contested half of it: `playbook-admin`'s page is
labelled *Playbook*, so the two words coincide there, and
`members-admin` / *Team* is the **first divergence** rather than an instance
of a settled pattern. It is accepted on its own reasoning, not on precedent.
`docs/playbook-program.md:159` supplies that reasoning: the page is titled
Team because that "supplies the container that makes 'members' read
naturally".

### 6. `/admin/roster` becomes `/admin/team`, and a bookmark breaks

Checked before deciding: the minted admin link redirects to
`/admin/playbook`, not here, and the page is otherwise reached only from the
shared admin header, whose entry is renamed with it. No spec names the URL.
So the only casualty is a typed or bookmarked `/admin/roster`, on an
admin-only surface with a handful of users, and no redirect is added for it —
a permanent redirect for a path nothing links to is a route to maintain
forever in exchange for one afternoon's convenience.

The header entry's key changes from `"roster"` to `"team"` alongside its
label and path, so `_admin_header.html`'s `current` comparison stays a
straight equality.

### 7. Nothing under `openspec/changes/` is touched

An archived change records what was proposed when it was proposed. Rewriting
its words to a vocabulary that did not exist then would make the record lie,
and the archives are where the reasoning behind the current specs is read
from.

The exclusion is `openspec/changes/**`, not `openspec/changes/archive/**`,
because **this change's own directory is under it**. `rename-the-roster-to-members`
carries the word in its directory name and several hundred times in its four
artifacts, and those artifacts quote the pre-rename specs as the evidence for
renaming them. A map that reached them would corrupt the argument that
justifies it, and the completeness check in section 8 would fail against text
that is correct.

Both exclusions are declared in section 1's table and re-declared in check 2
below, rather than left to be inferred, so a future reader can tell they were
decided.

**`docs/domain-map.md`'s stale `Principal` vocabulary is excluded too, and
this is where that is recorded.** Lines 191 and 198 still name `Principal` as
the `access` root model and describe a repo-owned principals file granting
access by SKU. Both were made false by `move-principals-to-roster`, not by
this change. Three reasons for leaving them:

1. They carry neither a `roster` nor a `person` stem, so no map row reaches
   them and no check searches for them. "Correcting" them means a hand edit
   outside the machine-checked half of a change whose whole warrant is that
   everything is inside it.
2. `AGENTS.md`'s *Incremental development and scope control*: an improvement
   noticed along the way that is not in the change's stated scope becomes a
   separate proposed change rather than being folded in.
3. A correct fix is not a rename at all. Line 198 describes a design — a
   YAML file granting access by SKU list — that no longer exists in any
   form, so repairing it is a judgement about the domain map's accuracy, not
   a substitution.

It therefore gets an entry in `docs/deferred-work.md`, which
`docs/proposed-change-order.md` names as the home for findings that are not
changes.

### 8. Completion is three checks, not a reading

1. **Faithfulness** — the difference between the script's output and the
   commit touches no line carrying an identifier (section 5). Its scope is
   section 1's input set: the whole tree minus the declared exclusions, so it
   covers the `launch` seams, the ten driving adapters and the two
   composition roots, not only the subtrees a task happens to name.
2. **Completeness** — a case-insensitive search for `roster` returns nothing
   outside `openspec/changes/**` and `alembic/versions/**` **other than the
   `preserve` tokens enumerated in section 2**, and no `Person`,
   `create_person`, `list_people` or `person_id` survives in `access` or in
   the seams `launch` reads it through. The preserved tokens are named in the
   check, not waved past it: a `roster` the check reports is either a missed
   rename or a row that should have been on the preserve list, and both are
   defects.
3. **No behaviour changed** — `uv run pytest` green across all three tiers,
   `ruff check`, `ruff format --check`, `mypy` and `import-linter` clean, and
   the test diff contains no changed assertion, only renamed identifiers and
   renamed expected strings.

Check 3's last clause is the one a reviewer must actually read, and it is
small: it is the reason the change is safe, and the only place a rename can
hide a behaviour change.

## Risks / Trade-offs

**`skip_specs: true` is a liberal reading of the marker** — the spec *text*
changes even though no *requirement* does. → The proposal states the reading,
names the alternative, and says why the alternative is worse. If
`openspec-change-reviewer` rejects the reading, the fallback is the full
delta set, whose archive behaviour is now known-safe by precedent
(`proposal.md` — *Capabilities*). Nothing else in the *approach* depends on
the choice; **the test-authoring exemption does** — taking the fallback
re-arms `openspec-test-writer` over ten `ADDED` requirements that already
carry coverage.

**A prose collapse silently changes a requirement's meaning.** *"An active
roster member"* → *"an active member"* is safe; a less careful collapse might
not be. → 39 requirements across 13 specs is a readable diff, and it is
reviewed as one. This is the residual risk the machine check does not cover,
and it is named here rather than left to be discovered.

**The rename lands under `share-the-unit-test-harness`**, which is queued,
unstarted, and touches many of the same 93 test files. → It is already marked
*last* in `docs/proposed-change-order.md`; it rebases onto this, not the
reverse. The script's re-runnability is what makes that cheap.

**`Members(members=…)` reads awkwardly in its own constructor.** → Accepted
deliberately (section 2, and the decision was put to the author against
`Membership` and `Team`). The alternative names either collide with the
entity's plural or claim a word — *team* — that a company will want for
something else.

**A missed identifier compiles.** Python will happily import a module that
still says `RosterStore` if nothing renamed it. → `mypy` and `import-linter`
both fail on a dangling name, and check 2 searches for the word directly. The
three together leave no silent path.

**The old `worker` container outlives the migration by seconds.**
`docker-compose.yml` runs two services from one image tag; `app`'s `CMD`
chain owns `alembic upgrade head`, and `worker` waits on
`app: service_healthy`, which `app` reaches only after that completes.
Compose recreates `app` before `worker` because of that dependency, so
between the migration landing and the old worker being replaced there is a
brief window in which pre-rename code can query `roster_people`. → The
failure mode is a scheduled job erroring and being retried by
`procrastinate`, on the order of seconds, once per deploy. Accepted rather
than engineered around: both services carry the same `${IMAGE_TAG}` and are
replaced by the same `up -d`, and a rename is not worth a two-phase
expand-and-contract migration when the program's Change 5 will recreate the
schema outright.

**A queued job payload naming a renamed seam.** Checked, and not
substantiated: the `roster` / `roster_reader` seams are module attributes
wired at composition, not serialised task keyword arguments — no
`procrastinate` task in the tree takes one. Recorded so it is not re-raised.

## Migration Plan

One Alembic revision on `c04d95ba6e31`:

```
upgrade:   rename table      roster_people  →  members
           rename table      roster_set     →  members_set
           rename constraint ck_roster_set_singleton
                                            →  ck_members_set_singleton
downgrade: the same three, inverted
```

No row is read, written or moved. The deploy runs `alembic upgrade head` on
container start, as it does for every change; the rename is a metadata
operation and takes a brief `ACCESS EXCLUSIVE` lock on two small tables.

**Rollback is ordered, and the natural order is the failing one.** The
downgrade runs **before** the reverted image is deployed. Taken the other way
round, the reverted image no longer contains this revision file, the database
sits at a revision the tree cannot resolve, `alembic upgrade head` fails at
container start, and the container never becomes healthy — which is exactly
the shape of the 2026-08 `BOOTSTRAP_ADMIN_IDENTITY` failure `AGENTS.md`
records under *Deployment and configuration*. So:

```
  1. run the downgrade against the live database
  2. then deploy the reverted image
```

The schema and the code move together and neither works against the other's
half; the ordering above is the only thing that makes that true in both
directions.
