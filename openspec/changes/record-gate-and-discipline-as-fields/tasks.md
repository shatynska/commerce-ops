## 3. Resolution and the configuration check

- [x] 3.1 Compose the resolution: given the field definitions, a map from each gate identifier in `GATE_SEQUENCE` and each `Discipline` value to the option identifier whose name matches it **exactly** on the identifier string — no case-folding, no trimming, no fuzzy match. `GATE_SEQUENCE` is the public alias of the identifiers; `_SPECIFIED_GATES` is the private tuple pairing each with its opening mode, and is not what this needs.
- [x] 3.2 Compose the gap in **two tiers**: the empty-identifier clause is assessed for a field whose identifier is present at all; every other clause only for a field whose identifier is present and **non-empty**. An identifier that is present but empty is reported as *configured with no value*, never as the field being *absent* — the two call for different repairs. The clauses, for a configured field: an identifier absent from the folder's fields; a field the read reports as **uninterpretable**, named as that and never as declaring no options; a field of the wrong type; a field declaring no options; a gate with no exactly-matching option; a discipline with no exactly-matching option; **the gate field's gate options not appearing in `GATE_SEQUENCE` order**; the gate field declaring two options named for the same gate, or the discipline field two named for the same discipline — **not** a duplicate under a name the system never resolves against, which makes no write ambiguous and must not disable a field. The order clause is load-bearing, not cosmetic — every other check passes on a field whose options name all eight gates in the wrong sequence, which is the exact failure the change exists to prevent, and it is what a hand-added option creates because an appended option lands last. Compose **no** option-level or order finding for a field found in a gap of the kinds that **withhold option-level findings** (empty identifier, absent, uninterpretable, wrong type, optionless) — those findings are that fault's consequences, not separate repairs; the duplicate-name kind is the exception, since such a field may still be missing options, and what it withholds is the **order** finding alone. Report **every** gap, not the first, and name what the field does declare where an option is missing, so a hand-typed mismatch is diagnosable. The type check is not optional — a multi-select declares options too, so optionlessness alone would let one through.
- [x] 3.3 Distinguish **unset** from **unresolvable**, **per field**: an unconfigured identifier means no writes and no report for that field, and must not be reported as a gap. The other field is unaffected. Cover the one-set-one-unset state explicitly. Treat an identifier that is **present but empty** as a **gap**, not as absent: absence is how a deployment declines a field, while an empty value is what a `secrets`/`vars` slip renders for a deployment that meant to opt in, and answering that with silence is how this repository lost a deployment once already. This closes that class mechanically rather than leaving it to 1.3's manual check.
- [x] 3.4 Give the gap a content identity over the **whole finding** — per field: the **set** of gap kinds found (drawn from empty identifier, absent, uninterpretable, wrong type, optionless, duplicate option name, missing options, wrong order — a field can be in more than one at once, so compare it as a set, not as a single value), the sorted missing option names, the duplicated names, and the gate-option order observed — omit the order observed **and** the order kind while a duplicate stands on that field, or a reorder during an unrepaired duplicate re-reports it — so a changed gap re-reports and an unchanged one does not. Identity over missing options alone is wrong: seven of the eight gap kinds name nothing missing — only *missing options* does — so a wrong-typed field repaired into a wrongly-ordered one would match the standing row and report nothing.
- [x] 3.5 Keep this pure: it takes field definitions and the playbook's fixed vocabularies and returns resolution plus gap. No I/O, so it is testable without ClickUp.

- [x] 4.3c Check the configuration on a pass where **no launch is active** — the check must not sit behind an early return on an empty launch set. - [x] 4.4 **Send no Custom Field value on the create call.** `create_task` is untouched by this change. ## 5. Reporting the gap

- [x] 5.1 Add the suppression table and its Alembic migration: the identity of the last gap **reported**, and when.
- [x] 5.2 Report through `MonitoringNotifier`, injected by `worker.py` as it already is for the overdue check — a new consumer, not new plumbing.
- [x] 5.3 Write the suppression row **only after successful delivery**; an undelivered report leaves the gap eligible on the next pass. Borrowed from `scheduled-jobs`' rule for a continuing outage.
- [x] 5.4 Clear the row on a pass that finds no gap, so a repair lifts suppression and a later gap reports again — **and on a pass performing no check because no field identifier is configured** — the design's own rollback leaves a row nothing would otherwise clear, so opting back in with the same gap standing would report nothing. Do **not** clear it on a stand-down, on a failed folder read, or on a pass that made no check because no launch folder is configured: a playbook flapping in and out of readiness would then re-report the same unrepaired gap on every ready pass, which is the flood the report-once rule, and the record 5.1 creates, exist to prevent.
- [x] 5.4a Where the store is shared with the per-launch writes, let a failed access **on which a report is in flight** — the read deciding whether to report, or the write recording one delivered — oblige a restore before the **first** launch is attempted. Not the clearing path: it runs when no gap was found, so nothing depends on it, and obliging a restore there let a benign fault end a walk. Narrowed during implementation and carried into the delta and design; where that restore **itself** fails, end the walk and fail the run, on the ground `One launch's failure does not stop the other launches being converged` gives for a failed recovery between launches, extended here to the pre-walk restore — this is the one path where a fault of this concern costs more than the field values, and the spec qualifies the guarantee by exactly this much. Otherwise, let a failure to read or write the suppression record cost the pass its Custom Field values and nothing else: log at warning level, continue, and do not fail the run. Write suppression for a report delivered on a pass that made **no** folder read — an empty-identifier finding — under the identity of what was actually composed, or that message repeats on every pass for as long as ClickUp is unreachable. Split the two accesses — a failed **read** of the record reports no gap on that pass (it cannot tell a standing gap from a new one); a failed **write after a delivered report** leaves the gap eligible again next pass, since the report has already gone out and cannot be recalled. Do not "fix" the latter by writing before delivering: that silences an undelivered gap permanently, which is what 5.3 forbids. It sits ahead of every launch on the pre-walk path, so an uncaught fault there aborts the pass before anything is projected. Where the store is shared with the per-launch writes, restore it to a state in which those writes can be recorded before attempting any launch — continuing against a store that cannot record is worse than not continuing.
- [x] 5.5 Let a delivery failure log and continue: it must not fail the pass, or the freshness evidence `scheduled-jobs` depends on goes stale for a channel outage.
- [x] 5.5a Across all four new swallow sites (4.3, 4.7, 5.4a, 5.5), do **not** absorb a cancellation or shutdown of the process running the pass. Reconcile with 4.3, which needs a catch wide enough for a malformed payload: catch broadly enough to include a parse failure, narrowly enough to exclude cancellation and shutdown — in this runtime that is catching `Exception` rather than `BaseException`, not a hand-listed set of error types. `launch-clickup-sync` requires a stopped worker to stop; a broad catch gives one that finishes its walk after being told to stop.
- [x] 5.6 Compose a message naming the field and every missing gate and discipline. Where no folder read completed, the message carries the empty-identifier finding alone and must not imply anything about options nobody could read. so one repair round closes them all — **and, where an expected option is missing, what the field does declare; where the order is wrong, the order found; where an identifier is present but empty, that the field is configured with no value rather than absent**. Both are composed into the gap by 3.2 and are easy to drop silently at the message boundary, which is the only place they are worth anything.
