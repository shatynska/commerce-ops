## Context

See `proposal.md` for the defect and the evidence. Six things about the code as it stands shape this design, and three of them were measured against the locked dependencies rather than assumed.

- **The blocking call is two frames below the coroutine.** `advise_sub_category` (`async def`) → `propose()` (plain `def`) → `running.invoke(...)` → LangGraph's sync path → `recommend` (plain `def`) → `structured.invoke(...)` → a blocking HTTP request. Any design that converts one frame and not the others leaves the block in place; the only question is which frames and how far down.
- **The worker is one loop.** `worker.py` runs `app.run_worker_async()` under a single `asyncio.run`. There is no second loop and no executor the pass hands work to, so "the loop" and "the process's ability to do anything" are the same thing here. This is why the defect is a defect and not a latency preference.
- **LangGraph 1.2.11 refuses to run an async-only node synchronously.** Measured, not inferred: a `StateGraph` whose only node is a coroutine raises `TypeError: No synchronous function provided to "<node>"` from `compiled.invoke(...)`. Decision 2 is built on this.
- **LangGraph 1.2.11 runs a *sync* node under `ainvoke` on a worker thread.** Also measured: the node body observed a different `threading.get_ident()` from the caller's. So the weaker half-fix is not merely inelegant — it works, silently, which is exactly what makes it the wrong choice (Decision 3).
- **Every stub runnable in all eight affected test files already answers `async def ainvoke`.** The proposal's original claim that the stubs must be taught it was wrong; the migration is at the call sites, not in the doubles. Five of the eight files already carry a module-scoped `anyio_backend` fixture and use `@pytest.mark.anyio`; three do not (`test_subcategory_advisor_graph.py`, `test_subcategory_advisor_finding_and_tools.py`, and the unit-tier `test_subcategory_advisor_schema_conversion.py`).
- **One of the eight is in the commit-time tier and fails misleadingly.** `tests/unit/step_handlers/listing/test_subcategory_advisor_schema_conversion.py`'s `_schemas_the_call_site_passed()` calls `propose()` inside a `try` and inspects `model.schemas` afterwards. A coroutine that is created and never awaited raises nothing and runs nothing, so `schemas` stays empty and the assertion downstream reports "the advisor never called `with_structured_output(...)`" — a message that accuses the subject of the test's own omission. It also emits a `RuntimeWarning: coroutine ... was never awaited`, which is the only honest signal in the failure and is not what a reader looks at first.

## Goals / Non-Goals

**Goals:**

- The advisor's model round-trip yields the loop, so one handler's latency costs the pass its own time and not the process's ability to do anything else.
- The blocking shape is not merely discouraged but hard to write again — by construction where that is available, by an asserted observable where it is not.
- An obligation in `launch-step-automation` that a handler which does not exist yet can be held to, with a boundary that answers the case the requirement most needs to answer: a dependency that offers no asynchronous entry point at all.
- Byte-identical behaviour on all six exits from `propose()`.

**Non-Goals:**

- Not making the pass run handlers concurrently. Serial invocation is `launch-step-automation`'s existing behaviour, it has rate-limit and ordering consequences of its own, and this change deliberately leaves it alone. The requirement added here must not be readable as licence for it, which is why it is stated as an obligation on the handler and carries an explicit disclaimer.
- Not hoisting the `langgraph`/`langchain_openai` imports out of the builders. `launch-step-automation`'s *Registering a handler does not load what the handler needs to run* forbids it and the module docstring explains why at length; nothing about going async pressures it, because `ainvoke` lives on the same compiled object as `invoke`. Recorded as considered-and-excluded so that "while you are in there" does not reopen it.
- Not enabling ruff's `ASYNC` rule group. This project selects ruff's defaults; turning on a rule group is a repository-wide decision with its own diff, and `ASYNC210` — the rule that sounds relevant — knows `httpx`/`requests` call sites, not a third-party graph's `.invoke`. It would not have caught this defect and would not catch the next one.
- Not fixing `omni_agent`'s `call_model` node, which has the same sync-node shape. Its caller already awaits `graph.ainvoke`, so it is thread-pooled rather than loop-pinning, and it is governed by `omni-agent`, not by this capability. A finding, recorded in `docs/deferred-work.md`, not folded in.
- Not tightening `Proposal.outcome: Any` / `finding: Any`, which `docs/deferred-work.md` already holds.

## Decisions

**Decision 1 — Both frames become async, and the model call is awaited at its own call site.** `propose()` becomes `async def` and awaits `running.ainvoke(...)`; `recommend` becomes `async def` and awaits `structured.ainvoke(...)`. Converting only `propose()` is not a partial fix but a null one: `graph.ainvoke` over a sync node hands the node to a worker thread, so the blocking call would move off the loop by accident of the framework rather than because the code awaits anything. Converting only `recommend` is worse — `propose()` would still call `invoke`, which after this change raises. The two frames are one edit.

**Decision 2 — The async node *is* the enforcement, and the tier asserts the observable the node cannot.** This settles the question `proposal.md` originally deferred here: *whether the tier additionally asserts that no blocking call is made, and how*. The answer is at three levels, because there are three places the block can come back and the requirement's own observable catches none of them.

> **Corrected 2026-09-02, after measurement.** An earlier draft of this decision claimed the loop-free test would *fail* for a blocking call introduced inside `recommend` itself. It does not. **LangGraph's `ainvoke` yields to the loop before it runs the node**, whatever the node body then does, so a companion task on that loop progresses either way — measured on `langgraph` 1.2.11 with an awaiting node and a `time.sleep` node, which are indistinguishable to that assertion. The test-writer found this and reported it against the decision rather than writing a test that only appeared to cover it; the correction is folded in below, and the third bullet's guard is now thread identity, which does discriminate. The earlier claim is left visible rather than quietly replaced, because "this assertion guards X" is exactly the kind of belief that should not be re-derived from a document that never admits it was wrong once.

- *At the graph level, enforcement is structural and needs no test.* Once `recommend` is a coroutine, `compiled.invoke(...)` raises `TypeError: No synchronous function provided to "recommend"` (measured above). A future author who reverts `propose()` to `running.invoke(...)` does not get a slow handler; they get a handler that fails on its first invocation, loudly, naming the node. This is strictly better than an assertion, because it holds for callers nobody wrote a test for.
- *At the model level, enforcement must be asserted, because both entry points are real.* `structured` answers `invoke` and `ainvoke` alike, so reverting the node's body to `structured.invoke(...)` inside an `async def` would work, block the loop, and pass every existing assertion — the exact defect, one layer in. So the stubs' **synchronous `invoke` raises** an `AssertionError` naming what happened, in the same idiom the stubs already use for `_generate` ("the advisor called the model directly instead of through `with_structured_output(...)`"). A revert then fails at the point of the mistake with a message that names it.
- *At the node's own level, the guard is thread identity — because the requirement's observable cannot tell a yielding node from a blocking one.* This is the level the earlier draft got wrong. A blocking call introduced directly inside `recommend`, belonging to no stub, is reached by neither guard above: the graph still has an async node, so nothing raises, and the stub's `ainvoke` is still what answers. And it cannot be caught by "other work progressed", because LangGraph has already yielded before the node body runs.

  What *does* discriminate is **which thread the dependency answers on**. Measured on `langgraph` 1.2.11: a synchronous node reached through `ainvoke` runs on a worker thread with a different `threading.get_ident()`; an awaited coroutine node runs on the caller's. So the stub records the thread it answered on, and the tier asserts it is the invoking thread. That assertion does double duty — it is also the honest half of the delta's *A framework's thread offload does not stand in for a dependency's asynchronous entry point*, which is otherwise not observable at runtime.

- *And one test asserts the requirement's own observable, for what it is worth and no more.* Structural guards say "the sync entry point was not used"; the requirement says "other work progresses while the handler waits". Those are not the same claim, and the requirement is stated with the second, so the tier asserts the second directly rather than only its proxies. It is kept **as the delta scenario's observable, with no claim to guard a revert** — the bullet above is what guards the revert.

  **That test may not be built on wall-clock timing.** No `asyncio.sleep(<positive>)`, no "it finished faster than N", no thread timing — `AGENTS.md` requires the agent tier to be deterministic, and a scheduling race dressed as an assertion is worse than no assertion. The observable is an ordering fact between two tasks on one loop, and it is asserted as one: the companion task is created before the handler is awaited, and the record is read at the moment the handler returns, not after the companion is awaited.

  **The mechanism is still single-yield, and the `asyncio.Event` alternative is still rejected** — the stub's `ainvoke` yields once and then answers unconditionally, rather than waiting to be released by the companion. The reason has narrowed, though: it is no longer "so it fails rather than hangs", since measurement showed it does not fail either. It is that an Event handshake would make the stub's answer depend on the companion having run, which turns a stub into a scheduler and would hang the suite on any change to the node's shape. A stub that answers unconditionally cannot hang the suite no matter what the node does.

**Decision 3 — `asyncio.to_thread` around the sync graph is rejected here, and permitted by the requirement elsewhere.** These are not in tension, and both halves are deliberate.

Rejected *here*: `await asyncio.to_thread(running.invoke, ...)` in `propose()` would unblock the loop, leave all eight test files untouched, and preserve `graph.invoke`. It is the cheaper change and it is the wrong one. It costs a thread per invocation for work that is pure I/O waiting; it keeps a blocking client inside a graph whose library offers a native async path, so the handler would be paying for a workaround to a problem it does not have; and — decisively — it leaves `graph.invoke` working, which means a later author who deletes the offload gets a silently loop-pinning handler back, with no failure at all. Decision 2's structural guard exists precisely because that silence is what let this defect ship.

Permitted *elsewhere*: the requirement's boundary case is a dependency that offers **only** a blocking entry point, where there is no native path to prefer. Refusing the offload there would forbid handlers the project has every reason to want, and pretending a native path exists would be a requirement nobody can satisfy. So the offload is compliant — with one condition, that the handler says why the dependency has no asynchronous entry point. Unexplained, an offload is indistinguishable from one nobody checked, which is the state this whole change exists to end.

**Decision 4 — The requirement is a property of the handler, with an observable; not a property of the pass.** Two framings were available.

(a) *A handler SHALL NOT block the loop it is invoked on.* Honest about being unenforceable by type, and useless unless it names something a test can watch.
(b) *The pass SHALL remain responsive while a handler is in flight.* Directly observable, and wrong for this change: `proposal.md` rules the pass's own behaviour out of scope, the pass is already correct, and a requirement on the pass would be satisfied by making the *pass* offload work — which is the concurrency change this explicitly is not.

(a) is taken, and the objection to it is answered rather than absorbed: the requirement names the observable ("while a handler's dependency has not yet answered, other work scheduled on the invoking loop progresses") so that it is testable at the handler's own level, without a pass and without a live model. Framing (b) is recorded here so that a later reader who notices the requirement is about a handler and its observable is about a loop does not "correct" it into a statement about the pass.

**Decision 5 — Behaviour preservation is asserted by the tests that already exist, not by new equivalence tests.** All six exits from `propose()` are covered today across the seven agent-tier files, over both the structured and the wire stub families. Those tests migrate to `await` and otherwise keep every assertion and every assertion message byte-for-byte. A test whose assertion changes during this migration is a finding, not an edit — the change claims to alter nothing about what the advisor produces, and an assertion that had to move would be the evidence against that claim. This mirrors `restore-the-skipped-unit-tests`' rule for the same reason.

**Decision 6 — `_graph()`'s `lru_cache` stays, unchanged, and is safe *in this deployment* — which is not the same claim as loop-agnostic.** "Is this cache now loop-affine?" is the first question a reader of an async conversion should ask, so the answer is recorded here rather than left to be re-derived. It has two halves, and only the first is unconditional.

*The graph itself holds no loop.* A compiled `StateGraph` holds nodes and edges — no connection, no task, no loop. Caching one across `asyncio.run` boundaries is safe on its own terms.

*What the graph reaches does acquire one.* This change moves `ChatOpenAI` from `httpx`'s synchronous client to its asynchronous one, and an async connection pool **is** loop-affine. So the safety here does not rest on "nothing changed underneath" — something did. It rests on two facts about this deployment: the worker runs exactly one `asyncio.run` (Context bullet 2), and `_graph()` is reached only from `advise_sub_category`, which is invoked only by the pass on that loop. One loop for the process's life, one caller, so the cached client is never handed to a second loop.

That is a narrower guarantee than the first half, and it is stated narrowly on purpose. A future change that adds a second invoking process, a second loop, or a second caller of `_graph()` invalidates this reasoning without touching the cache or this handler — so it is that change's business, and a reader arriving here from one should find the condition rather than a reassurance that no longer applies.

Generalising this into a **second** requirement — that a resource retained between invocations must not silently bind to the loop that created it — was drafted into the delta and then removed. It is a real obligation and a real hazard, and this change is precisely the one that introduces a loop-affine retained resource, so the temptation is understandable. It is still a second normative addition to a change whose proposal scopes one, and it would carry its own scenario and its own test. It belongs in a change of its own, and it is recorded here so that its absence from the delta reads as a decision rather than an omission.

## Risks / Trade-offs

- **The first live invocation exercises two never-run paths at once.** `docs/deferred-work.md` records that the advisor's supported path has never run against a real model, because the deployment holds no product a model can classify. After this change, the first real run exercises the async transport *and* the supported branch together, with neither previously observed in production. This is not mitigated, because it cannot be without a classifiable product; it is stated so the first live run is read as the first live run. That entry's own list of what is untested names only the verdict path, so `tasks.md` 6.1a amends it to name the transport too — its trigger to close already covers both, but the person acting on that trigger would otherwise have no reason to look for a stalled loop.
- **A misleading commit-time failure is possible during implementation, not after it.** If the source is converted before `test_subcategory_advisor_schema_conversion.py` is, the pre-commit tier fails with a message accusing the advisor of never calling `with_structured_output(...)`. `tasks.md` orders the test migration to make this unreachable rather than merely survivable, and names the message so that an implementer who sees it anyway knows what it means.
- **Stubs that raise on `invoke` are stricter than the subject requires.** If some future legitimate path calls the sync entry point, these stubs will fail rather than pass. That is the intended trade — the whole point is that there is no legitimate sync path — but it is a real constraint on later work, and a later change that needs one must change the stubs deliberately and say why.

## Migration plan

None. No migration, no new runtime variable, no schema change, and no change to the registered handler name `listing.subcategory_advisor`, so nothing is version-sensitive between the deployed process and the database. The change is a pure in-process conversion behind an unchanged public surface: `advise_sub_category`'s signature is what the registry holds, and it is `async def` before and after.
