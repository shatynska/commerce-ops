## Context

`src/commerce_ops/` currently holds a single flat `main.py` (FastAPI app + inline `GET /health` route), created by `deploy-health-endpoint` (still in-progress, paused at 8/18 tasks pending a companion infra change — unrelated to this restructure). `tests/` already has a module/layer scaffold — `tests/unit/<module>/{domain,application,infrastructure}/` — for four module names (`catalog`, `orders_inventory`, `support`, `analytics`) lifted directly from README's Scope section, created speculatively by `add-code-quality-tooling` before any domain module existed. See proposal.md for why that's a problem worth fixing now rather than later.

## Goals / Non-Goals

**Goals:**
- Establish a `src/commerce_ops/` layout that scales cleanly as `shared/` and the first real domain module fill in, without a later restructure.
- Apply README's own ports-and-adapters vocabulary (domain/application/infrastructure, driving/driven) consistently, rather than inventing parallel naming.
- Remove structure that isn't yet justified by real code, in both `src/` and `tests/`, consistent with this project's stated preference against designing for hypothetical future requirements.

**Non-Goals:**
- Does not scaffold `catalog/`, `orders_inventory/`, `support/`, or `analytics/` — only `products/`, the module work is concretely starting on.
- Does not implement any `products/` business logic — this change produces skeleton packages (`__init__.py`) plus the relocated `/health` route, nothing more.
- Does not resolve how `driven/` subdivides once it holds more than one occupant — tracked as an open question below, deliberately deferred.
- Does not touch `deploy-health-endpoint`'s CI/Docker/compose artifacts or its paused deploy tasks (section 5 there) — out of scope here.
- Does not scaffold anything for LangGraph agent graphs — per README, those belong inside each owning module's own `application/` layer (e.g. eventually `products/application/`), not `shared/` and not a single top-level file; no module has real logic yet, so there's nothing to scaffold. Noted here so a future reader doesn't look for a shared "graph.py" the way they might look for `main.py`.

## Decisions

**`shared/` is layered (`domain/application/infrastructure`) immediately; domain modules stay flat until they need the split.** Domain modules default to flat `domain/`, `application/`, `infrastructure/` with no further nesting, matching the "structure only what's justified" principle — but `shared/` is the one deliberate exception, because it's already known (from README) to be about to hold multiple concrete things: the Slack dispatch adapter, the marketplace-adapter layer, and the shared Postgres engine/session factory. Layering it now avoids the same churn this change exists to prevent elsewhere. Alternative considered: keep `shared/` flat too, split later — rejected because, unlike a not-yet-started domain module, `shared/`'s eventual contents are already named in README, not hypothetical.

**`driving`/`driven` — not `http`/`persistence` or similar — is the vocabulary for splitting an `infrastructure/` layer by direction.** Taken directly from README's own description of the infrastructure layer ("driving adapters that call into the application layer... driven adapters the application layer calls out to"). Alternative considered and rejected: naming by protocol/technology (`http/`, `persistence/`). This breaks down under its own weight — Slack's Events API is itself HTTP-delivered, and the marketplace-adapter layer isn't persistence, so protocol/technology names don't cleanly classify the concrete things `shared/infrastructure/` is already known to need. `driving/driven` classifies by direction instead, which holds regardless of transport.

**`driving/` and `driven/` stay flat (no `api/`/`slack/` or `persistence/`/`marketplace/` subfolders) until a second occupant per direction actually exists.** Even the direction-based split doesn't yet need a *sub*-split — `driving/` will hold exactly one thing (`health.py`) until Slack is added; `driven/` holds nothing yet. Naming that further split now would repeat the exact mistake this change is fixing (structure ahead of need). See Open Questions for what's deferred here.

**`products/` is the first (and only, for now) domain module; the other three from README's initial scope are not scaffolded.** README's Scope section names four domains as *planning* language, describing initial product scope, not a settled set of code module boundaries. Only `products/` is concrete work starting now; scaffolding the other three ahead of any of them being built would reintroduce the same speculative-structure problem this change removes from `tests/`.

**The speculative `tests/{unit,agents,integration}/{catalog,orders_inventory,support,analytics}/` folders are removed, down to `test_placeholder.py` per tier.** They named module boundaries no code has yet confirmed; keeping them risks them becoming the *wrong* scream if a real module's actual name or boundary differs. Future test folders get added alongside whichever source module first needs internal (non-black-box) tests — this change does not itself create a `tests/.../products/` folder; see the `tests/unit/test_health.py` decision below for why `products/` doesn't need one yet either.

**`tests/unit/test_health.py` stays flat at the tier root; `shared/` does not get a mirrored `tests/unit/shared/{domain,application,infrastructure}/` tree in this change.** AGENTS.md's testing tiers are organized `tests/unit/<module>/<layer>/` to mirror source layout, and this change is the first to give `src/` real module/layer structure to mirror — but `test_health.py` already tests `/health` as a black box through a real `TestClient` HTTP round-trip, which doesn't care which internal file the route lives in. Mirroring the layout now would mean creating empty layer folders with nothing unit-level to test inside them (no domain/application logic exists in `shared/` yet). The mirrored `tests/unit/shared/domain/` etc. gets created once something in `shared/` actually has internal logic worth a unit test — same "don't structure ahead of need" principle applied to `src/` elsewhere in this design.

**`src/commerce_ops/` (src-layout) is kept as-is, not flattened.** `src/` is an isolation boundary (prevents accidentally importing an uninstalled local package instead of the installed one — a well-documented Python packaging footgun), not a redundant wrapper; `commerce_ops/` is the actual importable package, named for the project. Hatchling already auto-discovers this layout without extra configuration. Alternative considered: flat layout (package at repo root) — rejected, no benefit here and loses the isolation guarantee for a project that will grow a Docker-packaged deploy pipeline, exactly where that footgun tends to bite.

**`/health` moves into `shared/infrastructure/driving/health.py` as an `APIRouter`; `main.py` becomes a pure composition root.** Matches `deploy-health-endpoint` task 1.2's own framing of `/health` as cross-cutting, not owned by a bounded context — this change just gives that framing an actual home instead of leaving it inline.

**`main.py` (the composition root) stays at `src/commerce_ops/`'s top level — a peer to `shared/` and `products/` — and does not move inside `shared/infrastructure/`.** This isn't a convention preference; it's a dependency-direction constraint. `main.py`'s job is to import and mount every module's router — today just `shared/`'s, but `products/`'s next, and later others. `shared/` exists so domain modules can safely depend on it; if the composition root lived inside `shared/infrastructure/`, `shared/` would need to import back from `products/` (and later modules) to do its job, inverting that dependency direction at the folder-structure level. The composition root has to sit above every module, including `shared/`, because it's the one place allowed to know about all of them. Alternative considered: nest it under `shared/infrastructure/driving/` alongside `health.py`, since both are "not owned by a bounded context" — rejected once the actual import direction was worked through; "not owned by one context" and "the thing that imports all contexts" are different responsibilities that happen to share a surface resemblance.

**Generalize README's Architecture-section wording (and AGENTS.md's Architecture summary, which carries the identical domain enumeration)** to drop the specific `(catalog, orders/inventory, support, analytics)` enumeration, adding a sentence that module boundaries are established incrementally as domain work actually begins rather than fixed upfront from initial product scope. Alternative considered: leave README as-is and only track the `products`/`catalog` mismatch as a deferred open question (the original plan, per the first review pass) — superseded once it became clear the more direct fix is removing the stale specific reference itself, rather than documenting around it. This doesn't decide whether `products/` is "the same as catalog" — it just stops README from asserting a specific, code-level answer to a question this change deliberately isn't settling. README's Scope section (the bullet list of initial *product* capabilities, not code module names) is untouched — it describes business scope, not a claim about `src/` structure, so it isn't subject to the same staleness risk.

## Risks / Trade-offs

- [Moving code already implemented by the in-progress `deploy-health-endpoint` change creates rework] → Scoped tightly: `deploy-health-endpoint`'s CI/Dockerfile/compose artifacts only reference `commerce_ops.main:app` (the ASGI entrypoint), not deeper source paths, so the move only touches `main.py` (and the new `shared/infrastructure/driving/health.py`) — not the packaging/deploy layer, and not `tests/unit/test_health.py`, which imports only `app` and needs no change.
- [Removing the `tests/` module scaffolding could read as silently reverting prior work] → Mitigated: proposal.md records the reasoning explicitly, so this is a documented, deliberate removal, not an unexplained one.
- [Generalizing README/AGENTS.md could read as papering over an unresolved naming question rather than answering it] → Not the intent: this change resolves the *staleness* risk (a specific wrong name sitting in an authoritative doc) without pretending to resolve the separate, genuinely open *naming* question (is `products/` the right long-term name) — see Open Questions.

## Migration Plan

This is a structural move on code that has not been deployed anywhere yet (`deploy-health-endpoint`'s deploy step is still blocked on a companion infra change) — no live system, no rollback mechanism needed. Steps: create `shared/{domain,application,infrastructure/{driving,driven}}/` and `products/{domain,application,infrastructure}/` skeleton packages; move the `/health` route into `shared/infrastructure/driving/health.py` as an `APIRouter`, mount it from `main.py`; confirm `tests/unit/test_health.py` still passes unmodified (it imports only `app` from `commerce_ops.main`); delete the speculative `tests/` module folders; generalize README.md's and AGENTS.md's Architecture wording; run `uv run pytest`, `ruff check`, `ruff format --check`, `mypy` to confirm nothing broke.

## Open Questions

- **How should `driven/` (and, later, `driving/`) subdivide once each holds more than one occupant?** Deliberately deferred — the earlier `persistence`/`marketplace` split was rejected for the same protocol/domain-mismatch reason `http`/`slack` was, but no replacement axis has been found yet. Revisit once there are two concrete `driven/` occupants to classify against, not in the abstract.
- **Is `products/` ultimately the right long-term name for this bounded context, or will it later prove to be the same thing README's Scope section calls "catalog," or something else again?** No longer a documentation-staleness risk (README no longer asserts a specific answer either way), but still a standalone modeling question worth revisiting once the module has enough real behavior to judge its own boundary by.
