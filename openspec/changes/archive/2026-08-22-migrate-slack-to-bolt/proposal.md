## Why

`README.md`'s Technology section names Slack Bolt as the Slack interface's technology. No Bolt is installed. `omni_agent/infrastructure/driving/slack.py` hand-rolls signature verification, event-type dispatch and the URL-verification challenge against raw `slack-sdk` instead.

That gap is about to widen. The pending `add-product-creation-clickup-task` change needs slash commands and modals, and its design.md commits to hand-rolling `application/x-www-form-urlencoded` parsing, the nested JSON inside the `payload` form field, a `views.open` call against Slack's ~3-second `trigger_id` budget, and `response_action: errors` for inline validation. Bolt provides every one of those directly. Building a second hand-rolled layer, then migrating both, costs more than migrating one now.

Two further defects are fixed on the way, because the migration touches the same code:

- **Blocking I/O on the event loop.** `products/infrastructure/driving/monitoring.py`'s `daily` route is `async def` and calls `post_monitoring_message()` synchronously, which calls `slack_sdk.WebClient.chat_postMessage()` — blocking HTTP. The event loop stalls for a full Slack round-trip on every daily run.
- **A graph rebuilt per message.** `omni_agent/application/use_cases.py`'s `answer_question` calls `build_production_graph()` on every invocation, constructing a `ChatOpenAI` and recompiling the graph each time, then invoking it synchronously.

This change was originally part of `revise-foundation-for-launch-mvp` and was split out after review found two of its premises false. Both were then verified directly against `slack-bolt` 1.30.0 and against the existing tests; the corrected findings are in design.md and are the reason this is its own change rather than a footnote in another.

## What Changes

- **`omni_agent`'s inbound Slack route is re-implemented on Bolt.** `slack_bolt`'s `AsyncApp` behind `AsyncSlackRequestHandler`, mounted at the same path (`POST /omni_agent/slack/events`), replacing the hand-rolled `SignatureVerifier`, the `url_verification` branch and the `event_callback`/`app_mention` dispatch.
- **The Bolt app is constructed with a custom `authorize` callable and no `token` argument**, so no `auth.test` network call is made. Omitting the argument is necessary but *not sufficient*: Bolt falls back to `os.environ["SLACK_BOT_TOKEN"]`, which would silently reinstate the call, so the helper also refuses to build when that name is present. See design.md, Verified Findings 1 and 7.
- **A shared construction helper** in `shared/infrastructure/driving/` gives each module a lazily-built, per-app Bolt instance, so `products` follows the same pattern when it gains inbound routes rather than inventing a second.
- **An event Bolt has no listener for is acknowledged**, instead of answering 404 as Bolt does by default. This is a new requirement on `slack-trigger`, covering behavior the current adapter has and Bolt does not. It is implemented with Bolt's own unhandled-request path (`raise_error_for_unhandled_request` plus an `@app.error` handler), which runs only after listener matching has already failed, rather than with a catch-all listener that could shadow the real one.
- **A bot-authored `app_mention` is acknowledged but not answered.** Constructing the app without `token` means Bolt's own self-event filter can never fire (see design.md, Verified Finding 4), so a listener-level guard on the event's `bot_id`/`subtype` is the sole mechanism preventing the bot answering its own posts. This is a second behavior difference from today's adapter, and it gets its own requirement.
- **Outbound Slack calls and model invocation become async.** `slack_notifier.post_monitoring_message` moves to `AsyncWebClient` and becomes a coroutine; `monitoring.py` awaits it. `answer_question` becomes a coroutine over `graph.ainvoke`, with the compiled graph built once rather than per message.
- **Two existing test files get fixture corrections**, unavoidably: their doubles are synchronous and cannot stand in for coroutines. Every assertion, expected value and postcondition is preserved. Exactly three things change: the doubles become awaitable, one substitution seam moves, and — in the acknowledgement-ordering test — a docstring and a failure message that describe FastAPI's `BackgroundTasks` as the deferral mechanism are corrected to describe Bolt's. That test's assertions stand unchanged, verified empirically against `slack-bolt` 1.30.0 rather than assumed. See design.md; this is stated as a decision because the split-out parent change wrongly claimed these files could stay untouched.

## Capabilities

### Modified Capabilities

`slack-trigger` gains four requirements and has two revised:

- **ADDED** "An Event With No Registered Handler Is Still Acknowledged" — an event Bolt has no listener for is acknowledged rather than 404'd, and a handled event type still reaches its handler.
- **ADDED** "Handling An Event Requires No Credential Verification Call To Slack" — no outbound Slack call to establish the system's own identity, at startup or in the request path. This is what the `authorize` construction exists to guarantee, and what keeps the unit tier free of real Slack I/O.
- **ADDED** "Bot-Authored Events Do Not Trigger A Reply" — a mention carrying `bot_id`, or a bot-authored `subtype`, is acknowledged but not answered.
- **ADDED** "A Request That Cannot Be Handled With Available Credentials Is Rejected" — a credential that a request needs being absent, or present but empty, yields 401 rather than an acknowledgement or a 500. That covers the signing secret, and — on requests that will actually reply — the bot token. Whether a request will reply is decided by a module-supplied predicate rather than a list of exemptions, so a `url_verification` challenge, an event type that is only acknowledged, and a bot-authored mention are all left alone when the token is absent. Without that, this requirement would contradict two others in the same delta. The bot-token case is a genuine behavior difference: today the route acknowledges first and the reply fails later inside a background task, so an absent token produces a 200 and silence. The requirement is scoped to requests that actually need the credential, so a `url_verification` challenge is still answered when the token is absent — otherwise this change would break the existing challenge requirement during any token rotation. It covers absence and emptiness only; a present-but-rejected token surfaces at delivery, since proving otherwise would need the identity call the sibling requirement forbids.
- **MODIFIED** "Slack App Mention Triggers Omni" — scoped to mentions authored by a person, with bot-authored ones pointed at the new requirement above. Its scenario is narrowed to match, its WHEN becoming "a person `@mentions` the bot"; nothing else in it changes. Without this the capability would hold two requirements giving opposite verdicts on a bot-authored mention.
- **MODIFIED** "No Sender Identity Restriction (Deferred)" — restated to say that suppressing bot-authored events is loop prevention rather than a sender-identity restriction, so the requirement's text no longer reads as contradicted by the guard above. No workspace member is treated differently from any other; that remains deferred exactly as before. Its existing scenario is unchanged, and a second scenario is added asserting that two different members' mentions are processed identically — making the deferred property directly testable rather than inferable from the first scenario alone.

`product-monitoring` is **not** modified. Its "Report Delivery Failure Is Decoupled From The Trigger" requirement describes the same behavior before and after — the `try`/`except`/log structure is identical, only awaited.

## Impact

- `pyproject.toml`: adds `slack-bolt` and `aiohttp`, both declared directly. `aiohttp` is **not** transitive — `slack-bolt` 1.30.0 requires only `slack_sdk<4,>=3.38.0`, and `slack-sdk` declares `aiohttp` solely under its `optional` extra. Bolt's async app and `AsyncWebClient` both need it, so it is an explicit dependency of this project rather than something inherited. Verified against both packages' published metadata.
- The `slack-sdk` floor lifts. `slack-bolt` 1.30.0 requires `>=3.38.0`, above this project's declared `slack-sdk>=3.36.0,<4` (`pyproject.toml:16`). Compatible — the resolver simply lands on `slack-sdk` 3.43.0, inside both — but the effective floor is now 3.38.0, and the declared pin is updated to say so rather than leaving the real constraint implicit.
- Rewritten: `omni_agent/infrastructure/driving/slack.py`. New: `shared/infrastructure/driving/slack_app.py`. Modified: `omni_agent/application/use_cases.py`, `products/infrastructure/driven/slack_notifier.py`, `products/infrastructure/driving/monitoring.py`, `pyproject.toml`.
- **Call sites of the two functions whose signatures change**, enumerated so the modified-file list above is verifiable rather than asserted. `answer_question`: defined at `omni_agent/application/use_cases.py:8`, re-exported from that module's `__init__.py`, and called in exactly one place — `omni_agent/infrastructure/driving/slack.py:39`. `post_monitoring_message`: called in exactly one place, inside `monitoring.py`'s `_attempt_post` (`:78`), which is itself called twice (`:100`, `:103`). No other production caller exists for either, so no file beyond those listed is affected.
- **Test files modified**, with assertions preserved: `tests/unit/omni_agent/infrastructure/driving/test_slack_events_endpoint.py` and `tests/unit/products/infrastructure/driving/test_monitoring_routes.py`.
- **Test files NOT modified**, and constraining the implementation: `test_main_slack_wiring.py` and `test_main_monitoring_wiring.py` each run `commerce_ops.main` in a fresh interpreter and run its lifespan with three named secrets absent, requiring success. Bolt app construction must therefore stay lazy and must never happen at import time.
- **The unit tier must make no outbound Slack call**, per `AGENTS.md`'s testing strategy, under which `tests/unit` is the fast mocked tier and real I/O belongs to `tests/integration`. Independently of that, an `auth.test` with a fake token returns 401 and fails every success-path test outright. This is what the `authorize` decision protects, and it is verified explicitly rather than assumed. `deploy-pipeline`'s "Pull Request Validation Gate" is **not** cited for this: its "without any host connection" clause is about the deploy host, as its two scenarios show.
- No Slack app reconfiguration: the Events Request URL is unchanged. No environment variable is added, removed or renamed.
- **A new deployment constraint**: the runtime must never carry the generic names `SLACK_BOT_TOKEN` or `SLACK_SIGNING_SECRET`. Bolt's constructor falls back to both, and an ambient `SLACK_BOT_TOKEN` would defeat the `authorize` construction that this change's central requirement depends on. The helper refuses to build when `SLACK_BOT_TOKEN` is present, and a test pins that; for `SLACK_SIGNING_SECRET` it logs a warning and continues, since that fallback is unreachable here and failing hard would break every Slack request in exchange for nothing. Both checks are membership tests rather than value reads, which is what keeps two names that must never be declared from colliding with `runtime-configuration`'s undeclared-read detection. The constraint is recorded here because it binds the deployment, not just the code.
- **Unblocks `add-product-creation-clickup-task`**, whose Slack-handling design decisions this supersedes. That change must be revised via `openspec-update-change` before it is implemented; it is unimplemented, so nothing is unwound.

### Deliberately out of scope
- **Inbound Slack routes for `products`** (slash command, interactivity). The shared helper is built so that change uses it, but no `product_agent` route is added here.
- **Durability of deferred work.** Bolt schedules listener work as an asyncio task, which is lost on container restart — the same limitation `BackgroundTasks` has today. This change neither improves nor worsens it; only a job runner fixes it, and that is a separate change.
- **`omni_agent`'s graph itself.** Its nodes, model choice and lack of tools are untouched beyond building it once and invoking it with `ainvoke`.
