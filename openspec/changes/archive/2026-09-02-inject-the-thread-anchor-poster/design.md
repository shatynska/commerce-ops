## Context

`ensure_launch_thread` sits in `launch/application/thread_establishment.py` and takes four collaborators. Two of them — `hold_lock` and `channel` — are injected ports. The other two are not: it builds its own `lru_cache`d `AsyncWebClient` from `os.environ["PRODUCT_AGENT_SLACK_BOT_TOKEN"]`, and it takes the anchor's product name, SKU and marketplace as three loose strings from whichever caller got there first. Its first parameter is additionally typed `AsyncSession`, so the application layer names SQLAlchemy in a signature that only hands the value on.

`launch_thread_delivery.py:12-17` states that this module exists on the infrastructure side precisely so the application layer never composes its own collaborators. That claim is true of the repository and of `transaction()` and false of the client, and `import-linter` cannot tell, because all 18 contracts govern edges inside `commerce_ops` and say nothing about third-party imports.

The four loose strings are the more expensive half. `launch-instance`:503 requires the thread reference to be established once and **never re-created**, so the anchor is permanent from the moment it is posted. Four driving adapters each assemble the same four fields from whatever their own catalog read returned — `slack_entry.py:566-572`, `gate_confirmation.py:243-257`, `automation_confirmation.py:165-171`, `automation_pass.py:617-623` — and three of the four fall back to empty strings when that read returned nothing. A transient catalog failure at the wrong instant therefore writes `SKU: ` / `Marketplace: ` into a header no later message can correct.

A note on citations: `proposal.md`'s line references were accurate when it was written (2026-09-01) and several have since moved, because `fix-launch-thread-mentions` edited three of the four call sites. They are left as written rather than retrofitted — the proposal is a record of what was seen then. Every line reference in this document and in `tasks.md` is resolved against the tree as of 2026-09-02, and every `docs/deferred-work.md` row is named by its heading and first cell rather than by line, because that file grows.

## Goals / Non-Goals

**Goals**

- The Slack client leaves `launch/application/`. The anchor's poster arrives as a port, like the lock and the channel already do.
- `post_monitoring_message` surfaces the `ts` it currently discards, which is the one missing capability that forced a third client into existence.
- `ensure_launch_thread` stops naming SQLAlchemy.
- The anchor is composed from one authoritative read, taken where the permanent record is about to be written, rather than from whatever four call sites happened to be holding.

**Non-Goals**

- The anchor's **wording**. `_compose_anchor_message` keeps composing the same four facts; `launch-entry`:10 and `launch-instance`:503 keep governing them. This change decides where the values come from, not what they say.
- The establishment race and its advisory lock, which are correct.
- `resolve_mention_target`, whose own defect was `fix-launch-thread-mentions`'s subject and is fixed.
- The two other `_get_slack_client()` copies, in `launch/infrastructure/driven/slack_notifier.py` and `briefing/infrastructure/driven/slack_notifier.py`. Both are in the layer where a client belongs.
- An `import-linter` contract forbidding third-party imports by layer. It is the obvious follow-up and a separate argument: the forbidden set would have to be enumerated for every layer of every module, and an incomplete one is worse than none.
- Renaming `post_monitoring_message` — see the decision below, which declines the invitation `docs/deferred-work.md`'s *Small cleanups* row *`post_monitoring_message` is misnamed* records.
- **The stuck-step report's broken notifier**, found while writing this design and recorded in `docs/deferred-work.md` under *The stuck-step report cannot reach the notifier the worker injects*. `automation_pass._report_stuck_step` calls `notifier.post_monitoring_message(channel=…, text=…, thread_ts=…)` while `worker.py:83` injects `briefing`'s notifier, whose signature is `post_monitoring_message(message: str)`; the call cannot bind, the `TypeError` is swallowed by the surrounding `except`, and no stuck step is ever reported. It is adjacent — same function name, same swallowing-`except` shape, one of the four call sites this change edits — and it is a live defect in a different capability with a different fix, so it belongs to its own change rather than being folded in. Named here so that a reviewer can see it was found and excluded rather than missed.

## Decisions

**`post_monitoring_message` returns the posted message's `ts`; no sibling function is added.** It already builds the client, already takes `channel` as an argument, and is already the function the launch-thread sites import and post through. The only reason `thread_establishment` built a third client is that this one discarded the response. Returning `str` rather than `None` is source-compatible with all three existing call sites — `gate_confirmation.py:259`, `automation_confirmation.py:193`, `slack_entry.py:574` — every one of which ignores the value today, so no caller is edited to accommodate it and no second code path can drift from the first.

A sibling `post_launch_message` returning the `ts` was the alternative. It would have left the discarding form in place beside the returning one, which is two functions posting through one client and differing only in whether they tell you what they posted — the shape that produced this defect at the level above.

**The rename this change was invited to fold in is declined, on size.** `docs/deferred-work.md`'s *Small cleanups* table, in its *`post_monitoring_message` is misnamed* row, records that the function is misnamed — it posts to whichever channel it is handed, and every launch-thread site hands it `launches_channel()` — and parks the rename for "while `inject-the-thread-anchor-poster` is already changing its signature". That reasoning assumed a local signature edit, and it is wrong on two counts.

**A rename driven by this name would edit the wrong side.** The name is carried by **two different functions in two modules**. `launch`'s takes `channel`; `briefing`'s takes a bare `message` and is what `worker.py` injects as `MonitoringNotifier`. Two call sites *inside* `launch` call the name on that injected collaborator rather than on `launch`'s function — `clickup_sync_job.py:200` and `automation_pass.py:656` — so a rename scoped by module, or by the name, would rename them and break the first while appearing to fix the second. (`automation_pass.py:656` is already broken for a related reason; see the non-goal above.) That is the durable argument, and it does not weaken as the diff shrinks.

**And the diff does not shrink far enough.** Measured over the function actually being renamed — `launch`'s, excluding those two injected-notifier calls — the scope is **14 occurrences over 5 source files** (`slack_notifier.py` 2, `gate_confirmation.py` 4, `automation_confirmation.py` 4, `slack_entry.py` 3, `launch_thread_delivery.py` 1, the last a docstring mention), plus the launch-side tests. For contrast, the counts an unqualified `grep` gives are 27 source occurrences and 42 test occurrences: of those, 11 source and 20 test belong to `briefing`/`shared` and their function, and both `Protocol` declarations at `shared/application/ports.py`:66 and `briefing/application/ports.py`:66 declare `briefing`'s signature, so — as task 1.4 establishes — none of that is the rename's cost. Even the honest 14-over-5, with its tests, is roughly twenty files of mechanical edits sharing none of this change's reasoning, which takes it past what `AGENTS.md` asks a change to stay inside: small enough to review in one sitting.

The row stays in `docs/deferred-work.md`, and this change replaces its now-spent trigger — *"worth doing while `inject-the-thread-anchor-poster` is already changing its signature"*, an occasion that has passed — with the measured scope above and the condition under which it does become worth doing. That is the honest disposition: a decision recorded where the next person looks, not a scope expansion smuggled in behind a one-line note.

**`db_session` leaves `ensure_launch_thread`'s signature entirely; `hold_lock` becomes a nullary port.** The parameter exists for exactly one expression — `await hold_lock(db_session, product_id)` — and nothing else in the function reads it. The proposal frames this as "stops naming `AsyncSession`", and the cheapest way to stop naming a type is to stop taking the value. `launch_thread_delivery` already holds both the session and the product identifier at the call, so it closes over them and passes `hold_lock: Callable[[], Awaitable[None]]`.

Retyping the parameter `Any` was the alternative, and it keeps a parameter whose only purpose is to be handed to a port that could have closed over it. A PEP 695 type parameter tying `db_session` to `hold_lock`'s first argument was the other; it types the relationship honestly, but the codebase contains no `TypeVar` and no PEP 695 generic anywhere, so it would introduce a construct for one call site. Deleting the parameter is strictly smaller than either and gives up nothing: binding the lock to the same session as the store is a fact the adapter can now state locally, in the one place that has both.

**The anchor is composed from one read, taken inside `ensure_launch_thread`, and only on the establishing path.** `ensure_launch_thread` takes a `read_product` port and calls it after the lock is held and after the early return for a launch that already carries a thread reference. So the read happens at most once per launch, at the moment the permanent record is about to be written, on the evidence available then — never on the reuse path, which is every message after the first.

Placing the read after the early return is not an optimisation. It is what bounds the whole risk this change introduces: a launch whose thread exists is completely unaffected by anything the catalog does.

**Where the product cannot be resolved, establishment is refused rather than degraded.** A read that raises, a read that answers `None`, and an absent `read_product` injection are one case — the system cannot say what the product is — and `ensure_launch_thread` raises instead of anchoring a thread with blanks in it. The asymmetry is the whole argument: a *degraded* anchor is permanent and has no repair path short of editing the database, while a *delayed* anchor costs one message that every caller already knows how to handle — three of them by retrying, and the launch confirmation by telling the submitter directly instead.

That every caller already knows how to is not an assumption; it is specified in all four places:

- `launch-entry`:12 — *"A started launch SHALL NOT be left unreported"* — covers the launch confirmation explicitly, naming "the thread cannot be established" as the case, and requires the direct message that `fix-launch-thread-mentions` implemented. This one path **substitutes** rather than retries: the anchor is simply not posted, and the launch's thread waits for whichever per-product message comes next. Nothing is lost and the submitter is told, which is what the argument needs, but it is not the same rule as the three below and must not be summarised as one.
- `launch-gate-progression`:141-144 — an undelivered ask is reported, records no delivery, does not fail the run, and is attempted again next pass while the gate still awaits confirmation.
- `launch-step-automation` — an undelivered pending result is delivered again later; nothing is recorded on a failed post.
- `launch-step-automation`'s stuck-step report — nothing is stamped as reported unless the delivery succeeded, so the next pass retries.

So no delta is needed in any of those three capabilities: refusal lands on a path each already specifies. `launch-instance`'s requirement is the one that changes, because it is the one that is currently silent about where the anchor's facts come from.

The tension worth naming is in `gate_confirmation.py:231-233`, which deliberately tolerates a failed catalog read — *"A catalog read failing must not withhold the ask: the decision is about the gate, and the identifier is enough to act on"*. That rule is about the **ask's body** and it survives untouched: the message still names the launch by identifier when the body's own read fails. What changes is that the *first* ask for a launch with no thread yet is now withheld and retried, because it cannot be delivered anywhere until a thread exists. The two are not in conflict — one governs a message that can be rewritten, the other a header that cannot.

The residual risk is a catalog outage lasting longer than a launch's first message: threads for launches started during it are not established, so their messages are retried rather than delivered. It is bounded to launches with no thread yet, it self-heals the moment the catalog answers, and no message is lost. A product cannot legitimately vanish from under a live launch — `catalog`'s public surface offers no deletion, and `launch-entry` registers the product and starts the launch atomically — so `None` means a fault, not a fact.

**A plain `RuntimeError`, not a new exception type.** No caller distinguishes this failure from any other delivery failure; each has one rule for "the post did not happen" and applies it. The function already raises `RuntimeError(f"no launch found for product {product_id.value}")` for the neighbouring impossible-state, and a second one naming the product and what could not be read reads consistently with it. A named type would be caught by nobody and would advertise a distinction the design deliberately does not make.

**The four driving adapters keep their own reads, and lose only the anchor's extraction block.** Each of the four reads the catalog for its own **message body** — the gate ask names the product, the pending-result ask names it, the stuck-step report names it — and those reads stay exactly as they are, degradation and all. What each loses is the four-line `sku_value` / `marketplace_value` block and the three extra arguments; `establish_thread_and_resolve_mention` is left taking the product identifier and the step.

This means the catalog is read twice on the establishing message: once by the adapter for its body, once inside establishment for the anchor. That is deliberate and it is the point of the change. Passing the adapter's already-read product in as a hint would restore exactly the property being removed — an anchor composed from whatever the caller happened to hold, including `None` — and would make the permanent record depend on which of four adapters fired first. One extra read, once per launch, is the price of the anchor being the same regardless of who triggers it.

**`read_product` is a module global on `launch_thread_delivery`, injected by both composition roots — and unlike the five others of that name, it takes the caller's session.** Reading the catalog crosses a module boundary `.importlinter` bars `launch.infrastructure` from crossing itself, so only a root may supply the reader — the seam `read_people` uses one module above, and that `gate_confirmation.read_product`, `slack_entry.read_product`, `automation_pass.read_product`, `clickup_sync_job.read_product` and `gate_progression_job.read_product` already use in five other places.

The shape must diverge from those five, and the reason is the placement decision above. Each of those five is called **outside** any transaction, and both readers the roots already hold reflect that: `main.py`'s `_RequestScopedCatalog.get_by_id` and `worker.py`'s `_read_catalog_product` each open their own `session()`, and `worker.py`:99-100 states the intent in as many words — *"It opens its own session — the pass may run for many launches, and this read is not part of their transaction."* Reusing either here would falsify that sentence: `ensure_launch_thread` runs inside `launch_thread_delivery`'s `transaction()`, which binds an explicit connection (`database.py:91`) and holds `pg_advisory_xact_lock` until it ends (`launch_thread_lock.py:72-74`). A reader opening its own session would check out a **second** connection from a pool built with no arguments — SQLAlchemy's default 5, overflowing to 15 — while holding both the first and the lock, and would extend the lock's critical section by a full catalog round-trip on every establishing message. At sustained concurrency that starves the pool with every holder waiting on a second connection.

So each root supplies `read_product(db_session, product_id)`, building `CatalogProductRepository` on the session it is handed. That is not a new liberty: `main.py`'s `_register_catalog_product` (`:114-141`) already builds the catalog's store on the launch adapter's own session, for the neighbouring reason — putting the catalog write and the launch write in one transaction. One connection, one round-trip inside the lock, and the divergence from the five carries its reason in a comment beside the global.

The application layer still names no session. `launch_thread_delivery` closes over its own, exactly as it now does for `hold_lock`, so the port `ensure_launch_thread` receives is nullary — `read_product: Callable[[], Awaitable[Any]] | None`. Both of its session-bound collaborators reach it the same way, which is what makes the pair legible.

Its disposition when absent is the **opposite** of `read_people`'s, and deliberately: a missing roster reader degrades a mention, which is an embellishment, so it is reported and the message goes out; a missing product reader means the anchor cannot be composed, so it refuses under the rule above. The two globals sit in the same module and must not be read as the same pattern, so each carries its own note saying which it is.

**The poster port is `(channel, text) -> ts`, and the `channel` port stays.** `ensure_launch_thread` keeps resolving the channel through the port it already takes and hands it to the poster, rather than the poster resolving its own. Keeping them separate is what keeps the application layer's statement of the rule visible: the anchor is a **top-level** message in the launches channel, and the reply that follows it is not. A poster that knew its own channel would move that fact out of the layer that states it into the adapter that happens to satisfy it.

## Risks / Trade-offs

- **A launch's first message can now be withheld by a catalog fault.** Accepted, with the reasoning above: bounded to launches with no thread, retried by every caller under an existing specified rule, self-healing, and traded against a permanent defect with no repair path. The alternative — post the anchor with blanks — is today's behaviour and today's defect.
- **One extra catalog read per launch.** On the establishing message only. Named rather than optimised away, because the optimisation is the defect.
- **`post_monitoring_message` keeps a name that misdescribes it for longer.** Accepted; the row and its cost stay recorded in `docs/deferred-work.md`.
- **Two module globals in one module with opposite absence policies.** Mitigated by a comment on each stating which policy it takes and why they differ, and by a test for each — the product reader's absence refusing, and the roster reader's absence still delivering.
- **A composition root that forgets `read_product` breaks every launch first-messaged in that process, permanently.** This is the sharpest new operational failure mode: under the refusal policy an un-injected reader is not a degradation but a hard, silent one — warnings in the log and no thread, forever, for those launches. Nothing at runtime guards it; `tasks.md` 6.3 makes it a verified fact in both roots rather than an assumption, and it is why that task exists as its own item rather than as a clause of 6.1 and 6.2.
- **The catalog read moves inside the establishment transaction and its advisory lock.** Held to one connection and one round-trip by the session-bound reader decided above; without that decision it would have been two connections from a pool of 5 (+10 overflow) held simultaneously per establishing message. The lock's critical section still grows by one catalog round-trip, which is a real change to a section that previously contained only local work.

## Migration Plan

None. No migration, no schema change, no new runtime variable. `PRODUCT_AGENT_SLACK_BOT_TOKEN` is read in one fewer place and is still read by its literal name in `launch/infrastructure/driven/slack_notifier.py:32`, which is what the environment-drift check scans for.

Launches that already carry a thread reference are untouched: their anchors were posted under the old rule and are not re-composed, because nothing re-composes an anchor. Launches whose anchor already reads `SKU: ` are not repaired by this change and cannot be — that is the damage it exists to stop, not to undo.
