## Context

`clickup_client.py` has eight public functions (`create_task`, `update_task`, `create_list`, `list_tasks`, `read_list_state`, `add_task_tag`, `folder_fields`, `set_task_field`), each independently doing `response = await get_client().<verb>(...)` followed by `response.raise_for_status()`. There is no shared request path today — the pattern is repeated at each call site. (`clickup-task-client`'s own failure requirement names them as seven enumerated *operations*, bundling "creating or updating a task" as one item — the two counts describe the same surface at different granularity, not a discrepancy.) Existing tests (`tests/unit/shared/infrastructure/driven/test_clickup_client*.py`) already substitute `get_client()` with `httpx.AsyncClient(transport=httpx.MockTransport(handler))`, so retry behavior can be exercised with a stateful mock handler (429 on the first call, 200 on a later one) without new test infrastructure. See proposal.md for why this change is needed.

**This job does not currently get `scheduled-jobs`' run-level retry.** That capability's "A Failed Run Is Retried With Increasing Delay" requirement is satisfied per-job by a procrastinate `retry=RetryStrategy(...)` passed at registration — `daily_briefing_job.py` does this. `clickup_sync_job.py`'s `@register_scheduled(name=TASK_NAME, schedule=SYNC_SCHEDULE, tolerance=SYNC_TOLERANCE)` call passes no `retry=`, and `job_runner.py`'s `app = procrastinate.App(...)` sets no retry default either, so a failed run of `launch.clickup.completion_pass` is not retried before the next scheduled tick, confirmed by reading both files. The proposal's "the next opportunity is the following scheduled tick" is accurate against the code as it stands, not merely against the observed incident.

This leaves a related question this design deliberately does not answer: should `reconcile_clickup_completions` also gain a `RetryStrategy`, bringing it into line with `scheduled-jobs`' requirement the way `daily_briefing_job.py` already is? See Non-Goals.

## Goals / Non-Goals

**Goals:**
- Ride out a brief `429` burst inside a single request, transparently to every caller, so one rate-limited moment in a pass does not fail every launch processed after it.
- Keep every other failure mode (400/404/5xx, connection failures, and a `429` that outlasts the retry budget) surfacing exactly as it does today — no caller-visible behavior change except timing.

**Non-Goals:**
- Proactive rate limiting (a token bucket or request pacing across the whole pass, or across processes sharing the token) to avoid hitting `429` in the first place. Reactive retry is simpler, requires no assumption about ClickUp's actual per-plan limit, and directly addresses the observed failure (a burst, not a sustained ceiling). If retries prove insufficient once this ships, proactive throttling is a follow-up change, not a decision this one needs to make now.
- Fixing the two Custom Field option IDs that 400 on every write for `lp.finance.001` — that is a ClickUp-side configuration issue, not a code defect, and unrelated to rate limiting.
- Any change to how `launch-clickup-sync` or the scheduled job treats a failure once the client surfaces one — that handling (log, mark the launch failed, continue the walk, fail the job run) is correct today and is untouched.
- Adding a `RetryStrategy` to `reconcile_clickup_completions` itself, so the run as a whole is retried per `scheduled-jobs`' existing requirement. That is a plausible complementary fix, but a coarser one for this failure mode: a retried *run* re-walks every active launch from the top, including ones that already converged, rather than retrying only the specific request that hit `429` — the reason this change targets the client instead of the job. Worth its own change if request-level retry proves insufficient; not a decision this one needs to make, and bundling it here would let one change grow to cover two independent concerns.

## Decisions

**One shared low-level send helper, not per-operation retry logic.** Introduce a single internal async function every one of the seven operations routes its request through, replacing each site's direct `get_client().<verb>(...)` + `raise_for_status()` pair. It performs the request, retries internally on a `429` response, and only then calls `raise_for_status()` and returns the response to the existing per-operation parsing code unchanged.
*Alternative considered:* a custom `httpx.AsyncBaseTransport` (or client event hooks) wrapping `get_client()`, retrying below the operations entirely. Rejected: it would touch one place too, but moves the retry outside the module a reviewer reads top-to-bottom against the `clickup-task-client` spec, and existing tests substitute the *client* (`get_client()`), not the transport in isolation — a shared function keeps the retry visible exactly where the seam already is, so existing MockTransport-based tests need only new response sequences, not new fixtures.

**Retry only on HTTP 429.** No other status, and no connection failure, is retried — each surfaces on the first attempt exactly as today. Retrying a 400 or 404 would just reproduce it while spending more of the very rate-limit budget this change protects; retrying a connection failure changes a different, already-correct contract (`ClickUp is unreachable` propagates immediately) that this proposal does not touch.

**Bounded backoff, `Retry-After` honored and capped.** Up to 3 retries (4 attempts total). Where ClickUp's `429` response carries a `Retry-After` header, the wait honors it, capped at 10 seconds per attempt so a large value cannot stall a single request — and by extension the whole pass — for an unreasonable time. A header present but not parseable as a plain count of seconds is treated the same as an absent one, falling back to the client's own backoff, rather than letting a parse failure raise an unrelated error out of the retry helper. Where the header is absent (or unparseable), fall back to a short exponential backoff (1s, 2s, 4s). Rationale: ClickUp's rate-limit windows are documented as per-minute, so a handful of seconds is enough to ride out a brief burst — the actual failure mode observed in production — without materially lengthening a scheduled pass; a launch still rate-limited past this budget fails exactly as it does today and is picked up on the next scheduled tick, unchanged.

**No new dependency.** Implemented with `asyncio.sleep` and a small loop — the policy is narrow (one status code, one header), and a general-purpose retry library (e.g. `tenacity`) would be a new dependency for a handful of lines of logic.

## Risks / Trade-offs

- **A launch rate-limited past the retry budget still fails the pass, same as today** → Intended, not a gap: the bounded retry targets the burst this proposal was written against, not a sustained ceiling. A genuine sustained rate-limit breach should still surface, exactly as `clickup-task-client`'s existing failure contract requires for everything past the carved-out case.
- **The permanently-failing Custom Field writes for `lp.finance.001` will now also retry-then-fail whenever they happen to hit a 429, adding latency without fixing anything** → Acceptable: those writes are already non-fatal per-field regardless of which status code they fail on (`_ensure_field_values` steps over any exception), so the added latency is bounded by the same retry cap as every other call, and the underlying option-ID problem is explicitly out of scope here (see Non-Goals).
- **Retrying lengthens the pass under sustained load** — the true worst case per request is up to 30s (3 retries, each waiting the full 10s `Retry-After` cap), not the 7s a no-`Retry-After` exponential fallback alone would cost → Bounded by the attempt cap and the per-wait cap regardless of which path is taken; even at 30s per request, a pass hitting several rate-limited requests in the observed case (seven launches) adds at most a few minutes, still comfortably inside the ten-minute scheduling window. A pass hitting rate limits on most or all of many more launches would add proportionally more, bounded linearly by the number of rate-limited requests times 30s — worth revisiting if `launch-clickup-sync` grows to cover hundreds of active launches, but not a concern at today's scale.
- **Multiple processes or passes sharing the same ClickUp token could still collectively exceed the limit even with per-request retry** → Out of scope (see Non-Goals); noted as a candidate follow-up if retry alone proves insufficient.

## Migration Plan

None needed. This is an internal, backward-compatible behavior change to the client with no data migration, no configuration flag, and no change to any caller's code or the client's public signatures. It ships through the normal PR → merge → deploy pipeline.
