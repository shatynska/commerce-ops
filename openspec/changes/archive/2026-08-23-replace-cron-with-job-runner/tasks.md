## 1. Dependency and schema

- [x] 1.1 Add `procrastinate` to `pyproject.toml` with a pinned major (`>=3.9,<4`); run `uv sync` and confirm `psycopg[pool]` arrives with it. If the dependency footprint differs materially from design.md's account, report before proceeding
- [x] 1.1a Tie the vendored schema (1.4a) to the installed runner version: add a test asserting the installed runner's schema version matches the one the migration vendored. `>=3.9,<4` permits a minor upgrade that ships schema migrations, and without this a routine `uv lock --upgrade` runs newer runner code against 3.9's tables — failing at runtime, in the window before `report-overdue-scheduled-runs` can report it
- [x] 1.1b **Confirm a libpq wrapper is present.** `procrastinate`'s `psycopg` arrives without one: a clean install pulls `psycopg` and `psycopg-pool`, and `import procrastinate` fails with "no pq wrapper available" until `psycopg[binary]` is installed — verified. `asyncpg` bundles its own, so neither a developer machine nor the built image is known to carry the system library. Declare the binary extra rather than depending on it being there, and check the **built image** too, not only a local `uv sync` — every test that imports the runner fails at collection without it, which looks like a broken suite rather than a missing library (design.md — "that driver needs a libpq wrapper it does not bring with it")
- [x] 1.2 Derive the queue's `psycopg`-style connection string from `DATABASE_URL` rather than delivering a second secret — the deploy renders one URL, and `docker-compose.yml` constructs it from `POSTGRES_PASSWORD`
- [x] 1.3 Add an Alembic migration installing the runner's schema, executing the multi-statement script through **asyncpg's own `Connection.execute()`** — reached from the raw driver connection under the bind (`op.get_bind().connection.driver_connection`; confirm the exact attribute path against the installed SQLAlchemy). Because the migration body runs synchronously inside `connection.run_sync(...)` (`alembic/env.py:80`), awaiting that coroutine needs the greenlet bridge, `sqlalchemy.util.await_only`.

  Do **not** use `op.execute` or `exec_driver_sql`: both are SQLAlchemy `Connection` methods that route through dialect execution and therefore through the same prepared-statement path that rejects multi-statement SQL — verified, `Connection.exec_driver_sql` goes through `_execute_context`. An explicit `$$`-aware statement split is the fallback, not the first attempt: it is the fragile branch (design.md — "Install the runner's schema through Alembic")
- [x] 1.4 Give the migration a `downgrade` that drops the runner's schema. The runner ships no teardown script, so enumerate the object classes by hand: tables, sequences, enum types, functions and triggers. This is likely the second-largest body of SQL in the change — budget for it rather than treating it as one line
- [x] 1.4a **Vendor the schema SQL into the migration** rather than reading it from the installed package at upgrade time. Reading it at upgrade time would make one revision produce different schemas depending on the installed runner version — the opposite of the version-pinning that justified using Alembic at all (design.md — "Install the runner's schema through Alembic")
- [x] 1.5 Verify `uv run alembic upgrade head` then `uv run alembic downgrade -1` both succeed against a local Postgres. "No orphaned objects" needs a real check, not a glance at `\dt`: query `pg_class`, `pg_type` and `pg_proc` for the runner's prefix and require empty results after the downgrade — a missed function or enum type is invisible to a table listing. If the execution mechanism in 1.3 proves impractical, stop and report rather than silently falling back to the runner's own CLI
- [x] 1.6 **Exclude the runner's tables from autogenerate.** `alembic/env.py` sets `target_metadata = Base.metadata` with no `include_object`/`include_name` filter, and `Base.metadata` describes `products`' models only — so once the runner's tables exist, the next `alembic revision --autogenerate` for any unrelated feature emits `op.drop_table` for each of them, destroying the run history. Add a filter rejecting the runner's table prefix (design.md — "a hazard that neither branch avoids")
- [x] 1.6a Put the filter predicate in an **importable module** under `src/commerce_ops/shared/infrastructure/driven/`, not in `alembic/env.py` — that file has no `__init__.py` beside it, a top-level `alembic` package would shadow the installed distribution, and its module body calls `context.config` at import, so a predicate defined there cannot be unit-tested. `env.py:10` already imports from `commerce_ops`, so the precedent exists
- [x] 1.6b Pass the filter at **both** `context.configure()` calls in `alembic/env.py` — the offline path (line 49) and the online path (line 61) — so the two cannot diverge
- [x] 1.7 Test the filter: assert it rejects the runner's table names and accepts a `products` table, so deleting it fails rather than silently re-arming the hazard
- [x] 1.8 Confirm empirically: with the runner's schema applied, run `uv run alembic revision --autogenerate` against a local Postgres and check the generated migration contains **no** `drop_table` for a runner table. Discard the generated file

## 2. Runner, job definitions and worker

- [x] 2.1 Add the runner's application object in `shared/infrastructure/driven/`, configured lazily so importing it requires no `DATABASE_URL` (consistent with `runtime-configuration`'s import/start requirement)
- [x] 2.2 Add the daily digest job in **`products/infrastructure/driving/`** — a scheduled job is a driving adapter, and this placement lets it reach `products`' own repository and notifier without `shared` ever importing a business module (design.md — "The daily job definition lives in `products`")
- [x] 2.3 The job calls the existing `run_daily_digest` use case through `centralize-database-session`'s `session()` context manager and `ProductRepository`, with **no change to the use case itself**
- [x] 2.4 Declare the daily schedule as `0 6 * * *`, **interpreted in UTC**. This task's stop-and-report branch has already fired and been resolved: the runner accepts no timezone parameter — `PeriodicTask` builds `croniter(self.cron)` without one and the deferrer evaluates from POSIX timestamps — so the requirement's earlier "explicitly configured timezone" wording was corrected, not the test (design.md — "The schedule is interpreted in UTC"). There is nothing to configure and nothing that can drift from the host. Do not weaken test 5.1: it asserts the due moments fall at 06:00 UTC as an absolute instant **and** do not change with the host's `TZ` — invariance alone is not UTC, since a runner fixed to any single zone would satisfy it. `TZ` on the container remains for log timestamps, not for scheduling
- [x] 2.5 **Set `App(periodic_defaults={"max_delay": float("inf")})`** on the runner's application object. The value is decided and verified, not an open figure: the default is 600 seconds and **drops** any due moment older than that, which fails the requirement outright (design.md — "A missed window runs once"). Do not substitute a large finite value — it reintroduces a silent-skip threshold, just further out. Confirm by test: 5.4 that the value has not been reverted to the default, 5.5 that several missed moments produce exactly one run rather than a replayed backlog, and 5.5a that a tick which already ran is not run again (spec: "A Window Missed While No Worker Was Available Is Run Once On Return")
- [x] 2.6 Configure the daily job's retry strategy: exponential backoff, small maximum attempts. Initial figures to record and revisit: 3 attempts, 60s base. **The runner's delay formula is `wait + linear_wait * attempts + exponential_wait ** (attempts + 1)`**, so "60s base" is the floor (`wait=60`) with a bounded exponential term on top -- 64s, 76s, 124s. Passing 60 as `exponential_wait` instead was rejected on contact: it yields 60s, one hour, then **2.5 days**, a third retry landing after two further daily runs and a failure message arriving days after the outage it reports
- [x] 2.7 Ensure a Slack delivery failure neither fails the run nor triggers a retry, while a database read failure does both (`product-monitoring` delta)
- [x] 2.7a Post the database-read failure message **only on the attempt the retry strategy will not retry** — read the attempt number from the runner's job context and the maximum from the single place task 2.6 declares it, so the two cannot drift apart. Without this, one outage posts one message per attempt, which is what the delta's "An intermediate failed attempt does not post" scenario forbids (design.md — "Retries")
- [x] 2.8 Add the worker entry point (`src/commerce_ops/worker.py`, beside `main.py` and `preflight.py`, outside the `.importlinter` containers), calling `configure_logging()` first, **importing the job definition modules so their schedules are actually registered**, and disposing the session provider's engine on shutdown. A worker that registers nothing runs healthy and schedules nothing — and with the healthcheck disabled by task 3.3, nothing would show it
- [x] 2.8a Run `preflight` in the worker's command chain, as `app`'s chain does. Its `command:` override otherwise drops that step, so a missing `PRODUCT_AGENT_MONITORING_CHANNEL_ID` would surface as a failed 06:00 job rather than a named report at container start. Running it also satisfies the configuration-check half of `deploy-pipeline`'s "Container Checks Its Runtime Configuration Before Migrating And Serving" for the second container. It does **not** make that requirement's "the migration and HTTP server SHALL then start" clause true of a worker, which serves no HTTP and runs no migration — so the requirement's subject stays ambiguous for a second container from the same image. Left deliberately: rescoping it to "each container started from the application's image" is a `deploy-pipeline` delta this change does not carry, and the ambiguity costs nothing while the worker's own preflight runs
- [x] 2.8b Apply the same `exec` requirement to the worker's command that `centralize-database-session` applies to `app`'s: without it `sh` stays PID 1, SIGTERM never reaches the worker, and its engine disposal and in-flight job handling never run
- [x] 2.9 Do **not** declare schedules for the weekly, biweekly, monthly or quarterly cadences; leave `run_pending_cadence_report` in place, unscheduled and uncalled
- [x] 2.10 **First confirm the runner's history carries, per run, which work it was, when it started, when it ended, and its outcome — and that a run retried more than once yields one record whose start is the first attempt's and whose end is the outcome that stopped it** (spec: "A run spans its retries"). The runner keeps one job row with a final status and an event row per attempt, so both the first and the last attempt's start are readable and the query has to choose; the requirement decides which — the `scheduled-jobs` requirement demands all four and the accessor is raw SQL over the physical tables. If the history does not carry them in that shape, stop and report: the requirement is what needs revisiting, not the query. Then add a last-success accessor in `shared/infrastructure/driven/`, over the runner's job history, returning the time of a piece of work's most recent successful run or a distinct never-succeeded result. This change specifies and tests that behavior (`scheduled-jobs`: "The most recent successful run can be identified"; test 5.9) and `proposal.md` claims queryability as its own deliverable, so it must be implemented here — `report-overdue-scheduled-runs` consumes it rather than building it
- [x] 2.10a Have the accessor query through `centralize-database-session`'s session provider, **not** through the runner's own connector. The sibling's freshness endpoint calls it from the HTTP process, which otherwise acquires the queue's second pool for a read that is not queue work — widening the two-driver footprint design.md scopes to the worker
- [x] 2.11 Move `_format_daily_message` and `_attempt_post` from `monitoring.py` into the daily job definition **unchanged** — they produce the digest's actual Slack text, and task 4.1 permits deleting the module they currently live in
