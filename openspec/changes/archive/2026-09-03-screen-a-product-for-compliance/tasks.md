## 1. Tests derived from the delta spec

Written before the implementation, from the delta's scenarios rather than from the code, by an author other than whoever writes the implementation (`AGENTS.md`, *Test design before implementation*).

- [x] 1.1 `tests/unit/step_handlers/strategy/` — the schema the screen passes is accepted by `langchain_openai`'s `_convert_to_openai_response_format` **and** by `langchain_core`'s `convert_to_openai_tool`, with no model call, no network and no credential. Obtain the schema by capturing the first argument to `with_structured_output` through the `build_graph(model)` seam, not by importing the wire model, so a call site that drifts from the symbol is detected. Assert the converted schema contains **no `oneOf` anywhere**, and that the verdict property is a plain string carrying an `enum` of exactly the three values. Covers *The schema is accepted by the provider's own conversion* and *The converted schema is the one the call site passes*.
- [x] 1.2 Each wire field carries a non-empty `description` in the generated JSON schema. Covers *Wire fields state when they are to be populated*.
- [x] 1.3 `tests/agents/step_handlers/strategy/` — the verdict table, one case per row, over a stubbed model. Pin **both** the verdict and the comment in every case so no two rows admit the same input. Together these cover *Every wire combination has a defined destination*:
  - `clear` + non-blank comment → satisfying outcome; rendered text carries the cited categories, the verdict and the comment (*A clear verdict proposes satisfaction*)
  - `flagged` + non-blank comment → non-terminal; assert the **reason states the screen flagged the product** and the rendered text carries the comment. Assert the wording, not merely that the outcome is non-terminal: an implementation routing every non-clear verdict to one reason passes a weaker assertion and violates the requirement that the three reasons be distinguishable (*A flagged verdict proposes a non-terminal outcome*)
  - `undetermined` + non-blank comment → non-terminal; reason states the question was not settled from what was given, and is **textually distinct** from the flagged reason (*An undetermined verdict proposes a non-terminal outcome*)
  - any verdict + comment absent, `""`, or whitespace-only → non-terminal, reason states no verdict could be read. Cover the `clear` row explicitly — it is the one where an implementation that checks the verdict before the comment goes wrong (*A verdict with an empty comment is treated as unreadable*)
  - a response validating against the schema at all → non-terminal, reason states no verdict could be read, and **does not** state that the product was flagged or clear (*An unreadable verdict is not reported as a judgement about the product*)
- [x] 1.4 The comment reaches the reader for every verdict that has one (*A verdict's comment reaches the reader*), and the routing is unaffected by what the comment says: a comment omitting the categories considered, the categories flagged, or the settling fact still routes on its verdict (*A comment's content is never checked by code*).
- [x] 1.5 A response whose comment reads as though it contradicts the verdict, in a direction the veto does not cover — a `flagged` comment reading as reassuring — still acts on the structured verdict (*A verdict is read from the discriminant, not the prose*).
- [x] 1.6 The contradiction veto, both directions:
  - a `clear` verdict whose comment states the **screen** could not screen the product → non-terminal, **and the rendered text carries that stated inability** rather than a bare "clear" (*A clear verdict carrying a stated inability is refused*)
  - a `clear` verdict whose comment states that a named **category** cannot apply to the product → still proposes satisfaction (*A statement about a category does not withhold satisfaction*). Without this second case the veto can be implemented as a phrase list that blocks the step on every pass for the product.
- [x] 1.7 The categories screened against come from the step's `description`: assert the prompt the model receives contains the description's text, **and** that the rendered text cites those categories for every verdict reached (*The step's description is what the product is tested against*, *The produced text cites what was screened against*). Then re-invoke with a **different** description and assert both the prompt and the cited categories changed accordingly, with no code change (*An edited description changes what is screened*). Two assertions must be able to fail independently: script a comment that names no categories at all and assert the rendered text names them anyway (this fails an implementation that leaves the citation to the model's comment); and use a description naming both a referenced list and a parenthetical of examples, asserting **both** halves reach the prompt and the citation (this fails an implementation that extracts a list from the description rather than carrying its text through).
- [x] 1.8 A step whose `description` is `None`, `""`, or whitespace-only → non-terminal, reason states the step names no categories to screen against, **and no model call is made** (*A step naming no categories is not a clear product*). Assert the absence of the call, not only the outcome: an implementation that prompts with an empty list and lets the model answer produces the same outcome text by accident and is the failure the requirement forbids.
- [x] 1.9 Model failure propagates (*Model failure is surfaced, not masked*):
  - a stubbed model raising on `ainvoke` → the exception propagates out of the handler; **no outcome is proposed and no non-terminal reason is produced** (*A failing model call surfaces as a failure*)
  - a stubbed model whose response content is not a plain string → the invocation fails visibly rather than yielding a coerced verdict (*Response content that is not a plain string surfaces as a failure*)
  - Assert propagation, not a caught-and-reported path. This is the test that stops a later broad `except` routing an outage into the unreadable-verdict reason, which is the adjacent route and the whole reason the requirement exists.
- [x] 1.10 A product whose marketplace-style value arrives as a value object reaches the model as that object's value — no type name, no field name, no quoting (*A value reaching the model is the value, not its object's rendering*). This is the advisor's already-paid lesson; the test is what stops it being re-paid.
- [x] 1.11 The resolution carries `finding is None` for every verdict (*No finding accompanies the outcome*), and the handler performs no lookup of its own, screening the product its context carries (*The product is taken from the context*).
- [x] 1.12 The screen invoked for a step whose identifier **and discipline** are not the ones it was written for, but which names categories, screens against them and proposes an outcome (*The screen does not test which step invoked it*).
- [x] 1.13 `tests/unit/step_handlers/strategy/` — importing the handler module registers its name and constructs no model, reads no credential and imports neither `langgraph` nor `langchain_openai` (*Registration loads nothing the run needs*). Assert against `sys.modules` in a fresh interpreter, not by inspection.
- [x] 1.14 Extend the existing cross-process registration check so both composition roots hold the new handler (*The handler is resolvable in every process consulting the registry*). `tests/unit/test_registrations_across_processes.py` is where two roots disagreeing is caught; adding a handler to only one root is the failure it exists for.

## 2. Implementation

- [x] 2.1 Create `src/commerce_ops/step_handlers/strategy/__init__.py` — the second discipline package, its docstring saying the same thing `listing/__init__.py`'s does: the directory name is the first segment of the handler names beneath it, a convention the registry does not enforce.
- [x] 2.2 Create `src/commerce_ops/step_handlers/strategy/compliance_screen.py` with `HANDLER_NAME = "strategy.compliance_screen"`.
- [x] 2.3 Add the wire model: a flat `BaseModel` with `verdict: Literal["clear", "flagged", "undetermined"]` and `comment: str | None`, each carrying a `Field(description=…)` stating what it is for and when to populate it. **No union at any level**, and no separate `error` field — `undetermined` is the structured home for an inability, which is why this schema has no contradiction state to convert (`design.md`, *One enum discriminant for three states*). The class docstring is sent to the model as the schema's `description`; keep the reasoning in a comment beside it, not in the docstring.
- [x] 2.4 Read the categories from `context.step.description`. Where it is `None`, empty or whitespace-only, return the non-terminal outcome from 1.8 **before** constructing a graph or calling a model — the early return is the requirement, not an optimisation.
- [x] 2.5 Build the prompt from the description's text **carried through unaltered** and the product's name. Do not parse the description into category names and do not select the part of it that looks like a list — an extraction step drops whatever does not match its shape, and the ordinary description names both a referenced list and a parenthetical of examples.
- [x] 2.6 Render the produced text as three parts: **the description's text as read, unaltered**, then the verdict, then the model's comment. The citation must not be taken from the comment — the verdict requirement forbids code from inspecting the comment's content, so a citation carried there is one nothing can assert (`design.md`, *The produced text cites the categories, rendered by the handler*). Prompt and citation must carry the same text, since the point of the citation is to say what was actually screened against.
- [x] 2.7 `build_graph(model)` / `build_production_graph()` split, one **async** node, `with_structured_output(..., include_raw=True)`, awaited via `ainvoke`. Import `langgraph` and `langchain_openai` **inside** the functions that build a graph, and `lru_cache` the production graph. A response that validated against no schema arrives as `None` and stays `None`, joining the "no verdict could be read" route.
- [x] 2.8 **Put no `try` around the model call.** A failing call must propagate: `launch-step-automation` reports the raising handler and records nothing, which is the specified treatment. The adjacent unreadable-verdict route is where a broad `except` would land, and routing an outage there records a client fault as the screen's judgement about a product.
- [x] 2.9 Implement the verdict routing exactly as section 1.3's table states, treating a blank comment as empty-or-whitespace and not merely `None`. Give the three non-terminal reasons three distinct texts — flagged, undetermined and unreadable name three different things that happened.
- [x] 2.10 Add the contradiction veto as a local regex over the comment only: a refusing subject (`i`, `we`, `the screen`, `this screen`) plus a refusal verb plus this screen's own objects (`screen`, `classify`, `determine`, `assess`). Match the **subject**, so that a statement about a category does not fire it (1.6, second case). Do **not** import or generalise `subcategory_advisor`'s `_ADVISOR_REFUSES` — the two match different sentences about different things, and `step_handlers/` grows no shared layer (`design.md`, *The contradiction veto is local and screen-specific*). Render a vetoed response so the stated inability is visible, not a bare "clear".
- [x] 2.11 Register with `@register_step_handler(HANDLER_NAME)`, returning `StepResolution` with `finding=None`. Read the product's values through their `.value`, never by stringifying the object carrying them. Test no property of the step other than its description.
- [x] 2.12 Add the module to `registrations.py`: one import beside `subcategory_advisor`, one entry in `HANDLER_MODULES`. Nothing there may read configuration at import.
- [x] 2.13 Touch no existing handler, and add no shared helper under `step_handlers/`. Where this screen repeats a shape from `subcategory_advisor`, it repeats it locally.

## 4. Activation and live verification after deploy

A green suite establishes that the handler behaves; it cannot establish that the step is wired to it. Activation is authoring, not deployment, and happens after the merge.

Carried out on 2026-09-02 against the merge of #155, deployed 23:01:26Z. Recorded here
rather than only in a conversation, since this section is the only place that says whether
the change actually worked. **It did, and it also found the one thing the plan said every
risk rested on.**

- [x] 4.1 Confirm the startup handler report names `strategy.compliance_screen` on the deployed host — the registry is what an activation is validated against, so this precedes 4.3.
      **Verified**, and more strongly than by the report: the handler ran and recorded outcomes attributed to `strategy.compliance_screen`, which establishes registration in the worker rather than merely in the process serving the admin surface.
