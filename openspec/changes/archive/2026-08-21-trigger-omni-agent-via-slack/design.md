## Context

See `proposal.md` - Why. Relevant constraints from the existing codebase and prior decisions:

- `add-omni-agent`'s design already fixed `omni_agent.application.graph.build_production_graph() -> CompiledStateGraph`, invoked as `graph.invoke({"messages": [HumanMessage(question)]})`, stateless, errors propagate uncaught. This change only adds a caller — it does not touch the graph.
- `deploy-health-endpoint`'s design already fixed the deploy shape this app runs under: one Docker container behind Traefik/Let's Encrypt at `fuperia.shatynska.com`, one image per commit SHA, deployed over a single forced-command SSH session that also delivers `docker-compose.yml` and a freshly rendered, never-committed `.env`.
- `README.md`'s Architecture section already names the target shape for Slack specifically: "one shared app/entry point (a single Slack Bolt process) that dispatches each incoming event to the relevant module's application layer... the same relationship the single FastAPI app already has to its per-module routes" — i.e. a driving adapter living in shared infra, not per-module.
- Today, `docker-compose.yml` has no `environment:`/`env_file:` at all, and `.env` (rendered per-deploy in `deploy.yml`) carries only `IMAGE_TAG` — so no runtime secret, including the `OPENAI_API_KEY` `omni-agent` already needs, reaches the container.

## Goals / Non-Goals

**Goals:**
- Pick the concrete library, module placement, and acknowledgement mechanism so implementation has no open technical decisions left.
- Satisfy the `slack-trigger` spec's verification, URL-challenge, and ack-timing requirements through library/framework mechanics chosen here, not hand-rolled reimplementations of solved problems.
- Close the runtime-secrets delivery gap using the deploy pipeline's existing single-SSH-session mechanism, not a new one.

**Non-Goals:**
- The sender-identity guard — explicitly deferred per the proposal and the `slack-trigger` spec's own "No Sender Identity Restriction (Deferred)" requirement.
- A generic multi-module Slack dispatch table. README's target architecture describes one shared entry point dispatching to "the relevant module," but with exactly one module (`omni_agent`) wired to Slack today, building a generic dispatcher now would be a speculative abstraction with a single caller. The route calls `omni_agent` directly; a real dispatch table is worth building once a second module needs Slack triggering.
- Any settings/config abstraction beyond ambient environment variables — consistent with `add-omni-agent`'s own deferral of that same decision.
- Deduplicating Slack's occasional event redelivery — see Risks below.

## Decisions

**`slack_sdk` directly (`SignatureVerifier` + `WebClient`) inside a plain FastAPI route, not `slack-bolt`'s `App`/listener/dispatch layer.** This revises the initial choice of `slack-bolt`'s `App` + `SlackRequestHandler`, made after that shape turned out to create two compounding problems rather than one: `App` construction needed deferring to avoid breaking the PR-validation CI gate and coupling `/health` startup to Slack reachability (see below), and — independently — a FastAPI route that fully delegates to `SlackRequestHandler.handle(req)` doesn't hand a real `BackgroundTasks` instance to a Bolt-registered `@app.event("app_mention")` listener; Bolt owns that request/response cycle internally, and no documented seam lets FastAPI's per-request `BackgroundTasks` reach into it. Using `slack_sdk` directly sidesteps both: `SignatureVerifier` and `WebClient` are the same official, tested components Bolt itself wraps internally for verification and posting — so the "don't hand-roll a security-sensitive check" rationale for using Bolt still holds — but neither performs any eager network call or requires the full listener-dispatch scaffolding at construction, and the FastAPI route keeps full ownership of the request, so attaching a real `BackgroundTasks` is direct, not routed through another framework's internals. `README.md`'s Architecture section describes "one shared app/entry point (a single Slack Bolt process) that dispatches each incoming event to the relevant module's application layer" (quoted in Context above); read at the level it's written — one shared entry point, in shared infra, dispatching to module application layers — this decision still satisfies it: there is exactly one Slack route, living in shared infra, calling into `omni_agent`'s application layer. What's revised is only which library implements that entry point's mechanics, not the entry-point shape itself; README's Technology section separately names "Slack Bolt / Slack Web API SDK" as a pairing, not `App` specifically as mandatory. Alternative considered: keep `slack-bolt`'s `App` and resolve the `BackgroundTasks` gap via Bolt's own lazy-listener feature (a background thread Bolt manages itself) — rejected because it moves the async boundary into Bolt's internals instead of code this project tests directly with FastAPI's `TestClient`, without buying back anything `slack_sdk` doesn't already provide for this single-event use case.

**Mounted at `src/commerce_ops/shared/infrastructure/driving/slack.py`, registered into `main.py` alongside `health.router`.** Matches README's description of Slack as one shared driving-adapter entry point living beside the FastAPI HTTP routes, not owned by `omni_agent`. `omni_agent` stays a pure application-layer module with no awareness of what triggers it — the same relationship it will have to any future HTTP route.

**`SignatureVerifier` and `WebClient` are constructed lazily, behind a cached factory (e.g. `functools.lru_cache`-wrapped `get_signature_verifier()` / `get_slack_client()`) invoked only when `/slack/events` actually receives a request — never at module import time.** `add-omni-agent`'s own design flagged this exact class of problem as a risk to revisit "when the Slack-triggering change adds a real entry point" — this is that change. The `deploy-pipeline` spec's `Pull Request Validation Gate` requirement runs `tests/unit`/`tests/agents` with no access to the `production`-scoped secrets this change adds and mandates it run "without any host connection," so `commerce_ops.main` (imported by the pre-existing `tests/unit/test_health.py`, and by this change's own tests) must import cleanly with `OMNI_AGENT_SLACK_SIGNING_SECRET`/`OMNI_AGENT_SLACK_BOT_TOKEN` absent. Deferring construction to first request keeps both `/health` and the existing/new test suites free of any Slack dependency at import or startup time — and, unlike Bolt's `App`, neither `SignatureVerifier(signing_secret=...)` nor `WebClient(token=...)` makes a live call to Slack's API at construction in the first place, so this is a defensive, testable pattern rather than a workaround for a verification call that would otherwise happen. The lazy factory is also the seam tests substitute fakes through, mirroring how `add-omni-agent` made the chat model a parameter rather than something constructed inside the graph.

**The FastAPI route owns the full request lifecycle directly, with `BackgroundTasks` used exactly as FastAPI intends.** The route: reads the raw body and headers; verifies the signature via `SignatureVerifier.is_valid_request(...)`, rejecting on failure; if the parsed body's `type` is `url_verification`, returns `{"challenge": ...}` immediately (a plain echo — not security-sensitive, needs no library support); if it's an `app_mention` `event_callback`, calls `background_tasks.add_task(handle_app_mention, event)` and returns `200` immediately, before `handle_app_mention` (which strips the bot-mention token, invokes `build_production_graph()`, and posts the answer via `WebClient.chat_postMessage`) ever runs. Because the route never delegates request ownership elsewhere, `BackgroundTasks` composes the normal way instead of needing a seam into another library's dispatch model. This is the mechanism that satisfies the spec's "Slack Events Are Acknowledged Within Slack's Timeout" requirement.

**The mention's bot-ID token is stripped from the event text before it's passed to `omni_agent` as the question.** Slack's `app_mention` event text includes the literal `<@BOTID>` tag; passing it through unstripped would leak an implementation artifact into the question the LLM sees.

**Reply as a new message in the same channel, not a threaded reply.** Simplest way to satisfy "post the resulting answer back to that same channel" with no added behavior to design around. Threading is a legitimate future refinement but isn't required by the spec.

**If invoking omni-agent fails inside the background task, a visible failure message is posted to the same channel instead of leaving the mention silently unanswered.** The background task runs after the HTTP response is already sent, so an uncaught exception there would otherwise surface only in server logs, with the channel seeing nothing — silently defeating `omni-agent`'s own "Model failure is surfaced, not masked" requirement at the one boundary that's supposed to carry it through to the user. `handle_app_mention` therefore wraps the `build_production_graph()` call, and on exception posts a short failure message via `WebClient.chat_postMessage` instead of re-raising into the void. See the new `slack-trigger` requirement "Answer Generation Failure Is Visible in Slack." This does not extend to `WebClient.chat_postMessage` itself failing (for either the answer or the failure message) — see Risks below; there is no further channel to report to once the one call meant to carry that report has itself failed.

**Secrets read from ambient environment variables (`OMNI_AGENT_SLACK_SIGNING_SECRET`, `OMNI_AGENT_SLACK_BOT_TOKEN`), no config object.** Same choice `add-omni-agent` already made for `OPENAI_API_KEY`; introducing a settings abstraction now, for three ambient env vars total, would be speculative.

**Deploy-pipeline change stays inside the existing single-SSH-session mechanism.** The "Render .env" step in `deploy.yml` gains `OPENAI_API_KEY`, `OMNI_AGENT_SLACK_SIGNING_SECRET`, `OMNI_AGENT_SLACK_BOT_TOKEN` lines sourced from `secrets.*` (same Environment-scoped `production` secrets already used for the deploy SSH key); `docker-compose.yml`'s `app` service gains `env_file: .env`. No new delivery path, no new SSH session — the file already travels in the one connection the `deploy-pipeline` spec requires.

## Risks / Trade-offs

- [Risk] Slack may redeliver the same event (e.g. `X-Slack-Retry-Num` after a slow ack), which could cause a duplicate answer to be posted since `omni_agent` and this adapter are both stateless with no idempotency store. → Mitigation: accepted for this change — an occasional duplicate reply is a minor nuisance, not a correctness issue; worth a dedicated de-dup mechanism only if it proves disruptive in practice.
- [Risk] `.env` changes from "carries a non-sensitive image tag" to "carries real secrets," while still being written to disk on the host and passed through `docker compose` the same way. → Mitigation: this is the same handling GitHub Actions secrets and the deploy SSH key already receive today (rendered fresh under `umask 077`, never committed); no weaker than the existing precedent, but worth confirming host-side file permissions on `/opt/commerce-ops/.env` match that expectation during implementation.
- [Risk] Coupling to `slack_sdk`'s `SignatureVerifier`/`WebClient` ties event handling to that library's version/behavior. → Mitigation: it's part of the technology `README.md` already commits to project-wide; not a decision specific to this change.
- [Risk] `env_file: .env` loads every line in `.env` into the container's process environment, including `IMAGE_TAG` — which exists only for `docker-compose.yml`'s own image-tag substitution, not as an application runtime value. → Mitigation: accepted; `IMAGE_TAG` isn't sensitive and the application has no reason to read it, so its presence in the process environment is inert, not a security or correctness concern.
- [Risk] If `WebClient.chat_postMessage` itself fails (invalid/revoked token, channel-not-found, rate limiting) — whether posting the answer or posting the failure message from the previous decision — the exception propagates uncaught inside the background task, and the mention is left silently unanswered from the channel's perspective, visible only in server logs. → Mitigation: accepted for this change, on the same basis as the event-redelivery risk above — this is a narrower, second-order failure (the reporting mechanism itself failing) rather than the primary case the new requirement addresses; worth handling explicitly (e.g. logging only, no further retry) if it proves disruptive in practice.

## Migration Plan

Purely additive on the application side (new route, new dependency) plus a small extension to an existing mechanism (deploy secrets). No data migration. Rollback: remove the Slack route/module, the `slack_sdk` dependency, the added `.env` lines in `deploy.yml`, and `env_file: .env` from `docker-compose.yml`. External prerequisite outside this repo: once deployed, the Slack app's Event Subscriptions Request URL must be pointed at `https://fuperia.shatynska.com/slack/events` (triggers the `url_verification` handshake this change implements), and the bot invited into the target channel(s).
