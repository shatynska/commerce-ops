## 3. Reading it

- [x] 3.1 Have `propose()` branch on the verdict from state. Supported proposes `Satisfied` with the recommendation; anything else proposes `Blocked` with the reason appropriate to that path — the existing wording for a genuine refusal, and a distinct one for each of the other three (3.4, 3.4a). Do not reuse one reason across the four
- [x] 3.1a Apply the prose veto (Decision 1a) **after** reading the verdict: a `supported` verdict whose recommendation states it cannot assign a node is treated as unsupported. The detector reads a statement that **the advisor** cannot assign a node; a recommendation calling a *rejected alternative* unsupportable is not that, and vetoing on it would block the step on every pass for that product (`design.md` — Decision 1a). **Refusal detection only** — do not also check that the recommendation carries a node path, its demands and a rejected alternative. That trigger keys on absence rather than presence, so it fires on well-formed prose it fails to recognise, and does so on every pass rather than once (`design.md` — Decision 1a, and *Non-Goals* for why the completeness obligation is left unenforced). Withholding only — no prose check may turn an unsupported verdict into a satisfying outcome, which is what keeps the served "never a satisfying one accompanied by text admitting there is no answer" enforceable
- [x] 3.2 Treat a verdict that is absent or neither-valued as unsupported, per Decision 2. Not a default parameter that silently supplies "supported" — the absence must reach the branch and be decided there, where a reader can see which way it goes
- [x] 3.3 Delete `_is_unsupported` and `_UNSUPPORTED_MARKERS`. The design deliberately keeps two mechanisms — the verdict decides, the prose may only withhold — so what must not survive is the old *decider*: leaving it in place would leave two answers to which one decides, and a future edit could reach for the wrong one. Do not satisfy this by renaming it into the veto; the veto's detector is narrower than the deleted list by the carve-out at 3.1a
- [x] 3.4 Leave the `Blocked` reason's wording as it stands **for a genuine refusal** — it already names the product and marketplace and states that no node choice could be supported
- [x] 3.4a Give each withheld path a reason naming what was actually wrong — no verdict reported, a verdict with an unrecognised value, or a supporting verdict contradicted by its own recommendation. Three distinct reasons, not one shared "fail-safe" wording: an unrecognised verdict reported as an absent one misstates the record just as surely as either reported as a refusal would. An operator reading the launch record has to be able to tell a verdict the advisor never gave from a classification it considered and declined; the same wording for both hides a model shortfall behind a plausible finding
