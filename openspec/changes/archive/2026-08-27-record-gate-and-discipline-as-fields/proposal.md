## Why

`tag-tasks-with-gate-and-discipline` put a step's gate and discipline onto its ClickUp task as tags, because a tag needs no prior existence and so cost the change nothing to reach. It works, and it buys the wrong thing.

A tag is an unordered member of an open vocabulary. The eight gates are neither: they are a **sequence** — `commit → order → listable → stock-ready → live → ignition → phase-one-complete → graduated` — fixed by `GATE_SEQUENCE` and validated against every loaded playbook by `_gate_sequence_faults`. Sorted as tags, that sequence reads `commit, graduated, ignition, listable, live, order, phase-one-complete, stock-ready`: alphabetical, and meaningless. A launch list cannot be ordered by the division the playbook is actually built along, which was the entire point of surfacing the gate.

A drop-down Custom Field holds its options in a declared order, so a view sorted or grouped by it reads in playbook order. Tags are additionally wanted for other characteristics of a task, which a two-purpose vocabulary would make ambiguous.

## What Changes

- **A projected task carries its step's gate and discipline as Custom Field values**, on two drop-down fields identified by `CLICKUP_GATE_FIELD_ID` and `CLICKUP_DISCIPLINE_FIELD_ID`. Set after the task is created, never inside the create call: keeping them off the path that brings a step's work into being is what makes "a field fault costs the field values and nothing else" true of every path this concern touches but one.
- **BREAKING (to the unarchived predecessor): the projection stops writing `gate:` and `discipline:` tags.** `clickup-task-client`'s tag operations are untouched and remain available — tags are being freed for other characteristics, not withdrawn.
- **The two fields are configured by hand and never by this system.** ClickUp's public API documents no way to create a Custom Field or edit its options, and the undocumented routes that do exist are not a contract this system will depend on (design.md records the measurements). The system reads the field configuration; it never writes it.
- **The field configuration is checked once per pass, before any task is written**, by one read at folder scope, and a gap is reported to Slack. One finding is established by the configuration alone and needs no read: an identifier rendered blank is reported whether or not ClickUp could be reached, so the catch for a mis-rendered deployment does not depend on the service whose configuration is in question. A gap is, per configured field: an identifier present but **empty** — reported as configured-with-no-value rather than as absent, since a mis-rendered blank and a missing field call for different repairs; a pinned field the folder does not include, one the read could not interpret — named as that, never as declaring no options — one that is not a single-valued field over an ordered option set, one declaring no options, one whose options do not name all eight gates or all twelve disciplines exactly, the gate field declaring two options named for the same gate (or the discipline field, for the same discipline), **or a gate field whose gate options are not in playbook order** — the last because ordering is the whole reason to prefer a field to a tag, and every other check can pass while the order is wrong.
- **A continuing gap is reported once, not on every pass**, mirroring `scheduled-jobs`' rule for a continuing outage, with suppression written only after a report is delivered and lifted when the configuration is repaired.
- **No value is written to a field found in a gap of the kinds that withhold writes** — an empty identifier, an absent, uninterpretable, wrong-typed, optionless or duplicate-named field — so it is left alone rather than written to once per task. A field merely missing one option still receives every value that does resolve.
- **One path, and only one, is excepted from that guarantee**: where the record suppressing repeated reports shares a store with the launches' writes and the pass cannot restore it, the walk ends and the run is recorded as failed — because continuing would write to ClickUp and lose the record of the write, which `launch-clickup-sync` already judges worse than stopping.
- **A gap never stops the pass.** Projection, correction and completion intake continue; the tasks written during a gap carry every other field and simply lack the one that cannot be set. Nothing about a gap is among the things that make a run fail — the run's outcome is settled by `launch-clickup-sync`'s *One launch's failure does not stop the other launches being converged* and by the stand-down requirement, and this change takes nothing away from either.
- **An absent variable is an opt-out, not a fault, and each field is independent.** A deployment that pins neither field id writes no values and reports nothing — it has declined the capability; a deployment pinning one records and reports on that one alone. A variable that is set and does not resolve — an empty value included — is a misconfiguration worth waking someone for. Because `deploy.yml` renders a blank for an unset secret, both lines are rendered **conditionally**, so declining is expressible as absence rather than arriving as a blank.
- **A value that disagrees with the step is corrected.** Unlike a tag, a Custom Field is single-valued and wholly determined by the step, so a divergence is drift rather than a person's own meaning. This retires the predecessor's accepted defect that *"a step moved to a different gate keeps its old gate tag"* — wherever the new gate resolves to an option; inside a gap the defect survives, bounded to the gap and reported as one.

### Non-goals

- **Creating or repairing the fields, their type, or their options.** Named above; the reasoning and the measurements are in design.md.
- **Any other Custom Field.** Only the two the playbook is divided along.
- **Tags for other characteristics.** The client keeps its tag operations; what is written into them next is a separate change.
- **Backfilling a `graduated` launch.** Excluded from projection and reconciliation entirely, exactly as the predecessor left it, so its tasks are neither retagged nor given fields.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `launch-clickup-sync`: **one added** requirement — a projected task carries its step's gate and discipline as values on two configured Custom Fields, corrected when they disagree, with a per-task failure costing the field and nothing else. **One added** — the field configuration is checked once per pass before any task is written, a gap is reported to Slack once rather than repeatedly, and a gap never stops the pass. **One modified** — the projection requirement, whose assignee paragraph carries a cross-reference to the tag rule that this change repoints at the Custom Field rule. **One removed** — the predecessor's tag requirement, whose subject this change takes over.
- `clickup-task-client`: **two added** requirements — reading the Custom Fields available in a folder, and setting a Custom Field value on an existing task. Nothing is added to the create: the projection deliberately keeps these values off the create call. **Two modified** — the read of a list's tasks additionally reports each task's Custom Field values, and the failure-surfacing enumeration is extended to cover the new operations.

## Impact

- **Depends on `tag-tasks-with-gate-and-discipline` being archived first.** That change is merged into `main` but unarchived, so `openspec/specs/launch-clickup-sync/spec.md` records no tag requirement at all — this change's REMOVED delta has nothing to remove until the predecessor's deltas are folded into the baseline. The ordering is a hard prerequisite in the shape `report-overdue-scheduled-runs` declared against `replace-cron-with-job-runner`, not a preference.
- **Two new runtime variables**, each requiring the four steps `AGENTS.md` sets out: an Environment **secret**, a `secrets`-sourced line in `deploy.yml`, a declaration on the settings model, and a mirror in the declared set `tests/unit/shared/application/test_settings.py` compares against. Both are declared **optional**, which is the classification that makes the opt-out expressible: `runtime-configuration` has each declaration carry "whether it is required or optional", and marks only *required* variables startup-critical or not. An absent optional variable is not a configuration fault, so a deployment declining the capability produces no report — which is the whole point. That capability needs no delta. Read them by their literal names — the drift check detects consumption by scanning for the name.
- `src/commerce_ops/shared/domain/clickup.py` — `ClickUpTaskState` gains the task's current Custom Field values; a value object for a field's definition and its ordered options.
- `src/commerce_ops/shared/infrastructure/driven/clickup_client.py` — `folder_fields` over `GET /api/v2/folder/{folder_id}/field`; `set_task_field` over `POST /api/v2/task/{task_id}/field/{field_id}`; parse and normalise each task's `custom_fields` in `_task_state`. `create_task` is untouched.
- `src/commerce_ops/launch/infrastructure/driven/clickup_sync.py` — resolve each step's gate and discipline to an option id, set them after a task is created, correct them on a mapped task, and let a per-task field failure warn and continue. The tag composition (`_step_tags`, `_missing_tags`, `_ensure_tags`, `_OWNED_TAG_PREFIXES` and their call sites) is **removed** — verified by grep over `src/` and `tests/`, not by a green suite, per the predecessor's task 3.0a.
- `src/commerce_ops/launch/infrastructure/driving/clickup_sync_job.py` — one folder-scope read per pass, ahead of the launch loop and after the playbook stand-down; the resolved options threaded into `converge_launch`; the gap reported through the `MonitoringNotifier` port `worker.py` already injects for the overdue check.
- **A pure resolution-and-gap component**, taking field definitions plus the playbook's fixed vocabularies and returning the resolution and the gap with no I/O, so it is testable without ClickUp; and a repository for the suppression record. Both belong to `launch` — the component in its application layer, the repository in `infrastructure/driven` — and neither reaches across a module boundary `import-linter` does not already permit.
- **One migration**, for the suppression record that keeps a continuing gap to one message across worker restarts. In-memory suppression is not sufficient for the reason `report-overdue-scheduled-runs` already gives: "so a worker restart does not resume the flood."
- **ClickUp API budget**: one folder read per pass, plus a one-time correction of up to two field writes per existing task, plus two writes per newly created task, paid once each — roughly +360 on a launch's first pass and nothing on later passes, the price of keeping these values off the create call — the same order as the predecessor's tag backfill, and convergent in the same way, so a rate-limited pass resumes on the next one.
- **Scope note.** This change could be split — writing the fields, then reporting a gap — and `AGENTS.md` prefers splitting where a change covers independent concerns. It is kept whole because the split's first half ships a state in which a misconfigured field fails silently, which is the defect this change exists to prevent. The reviewer is invited to disagree.
