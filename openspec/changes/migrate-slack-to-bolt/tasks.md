## 2. Shared Bolt construction

- [ ] 2.1 Add `shared/infrastructure/driving/slack_app.py` with a factory building an `AsyncApp` from four things: an **app identity** (the cache key of task 2.6), a **signing secret**, a **bot-token accessor**, and a **`will_reply(body) -> bool` predicate**. The secret builds the app; the accessor and predicate are consulted per request by the middleware of task 2.2b. A predicate, not a set of exempt event types — the helper must not need to know that "event type" is the discriminator, and enumerating exemptions has twice proved to be one case short (design.md, Verified Finding 9) Each module reads its own variables directly from `os.environ`, not via `get_settings()`, whose validation would raise where a 401 is required (design.md, "A request arriving while the signing secret is absent or empty")
- [ ] 2.2 Construct it with **no `token` argument** and a custom async `authorize` callable returning a fixed `AuthorizeResult` carrying the bot token. Passing `token` alongside `authorize` makes Bolt install `AsyncSingleTeamAuthorization` and ignore the `authorize` — `if self._token:` wins over `elif self._async_authorize is not None:` (design.md, Verified Finding 1)
- [ ] 2.2a Before constructing, raise if **`SLACK_BOT_TOKEN`** is present. Construction is lazy, so this fires on the first Slack request and yields a 500 — the right answer for a deployment this change declares invalid, and pinned by task 7.9 rather than left emergent. For **`SLACK_SIGNING_SECRET`**, log a warning and continue: its fallback is unreachable here, so failing hard would break every Slack request including the `url_verification` challenge, in exchange for nothing (design.md, Verified Finding 7)
- [ ] 2.2a(i) Write both checks as **membership tests** — `"SLACK_BOT_TOKEN" in os.environ` — never `os.environ[...]`, `.get()` or `os.getenv()`. This is required, not stylistic: the drift test's scanner records only subscripts and `.get`/`getenv` calls, and its source-reads-must-be-declared direction "admits no exemption at all", so a value read of a name that must never be declared would be unresolvable. A membership test asserts a name's absence rather than consuming a value, which is the distinction that check draws (design.md). Presence, not truthiness, is the rule Omitting the `token` argument is **not** sufficient: `async_app.py:219` does `token = token or os.environ.get("SLACK_BOT_TOKEN")`, so an ambient value makes `self._token` truthy and silently restores the `auth.test` call. No argument value prevents the fallback, so the guard is a precondition check, not a parameter (design.md, Verified Finding 7)
- [ ] 2.2b Pass a **`before_authorize` middleware** that returns `BoltResponse(status=401)` when the bot token is absent **or empty** (`if not token` covers both). Do **not** put this in `authorize`: returning `None` there yields 200 and raising yields 500, both of which "A Request That Cannot Be Handled With Available Credentials Is Rejected" forbids (design.md, Verified Finding 9)
- [ ] 2.2b(i) Pass through a `url_verification` request — required, because `AsyncUrlVerification` runs *after* authorization. Do **not** add an `ssl_check` branch: `AsyncSslCheck` short-circuits at position 1, before this middleware, and detects it as `body["ssl_check"] == "1"` rather than by `type` anyway
- [ ] 2.2b(ii) Require the token exactly when the module's `will_reply(body)` predicate is true, and pass through otherwise, so no request the system was never going to answer is rejected for lack of a reply token (`slack-trigger`: "A Request That Cannot Be Handled With Available Credentials Is Rejected", fourth and fifth scenarios). An unforeseen **request class** fails closed, since anything not recognised as reply-free is treated as replying. Treat a predicate that **raises** as `True` as well — an exception escaping `before_authorize` becomes a 500, which the requirement forbids
- [ ] 2.2b(iii) `omni_agent`'s predicate returns False for an `event_callback` whose event type has **no registered reply-producing listener** — keyed on the registration, not on a literal list of type names — and for an `app_mention` carrying `bot_id` or a bot-authored `subtype`. The registration keying is what extends fail-closed to unforeseen *event types*; a literal whitelist would exempt a newly-registered listener's type and let its reply fail silently, which is the enumeration problem relocated rather than solved. The bot-authorship half duplicates the listener guard of task 3.5 deliberately, at a different layer (design.md); share one helper so they cannot drift
- [ ] 2.2c Keep `authorize` itself to supplying the `AuthorizeResult` from whatever the accessor returns, empty string included, with **no** token-absence branch, assertion or raise. A carved-out request reaches `authorize` with the token still absent and must not fail there — it never uses the injected client, since it is acknowledged and dropped without a reply. Raising here would turn exactly those requests into the 500 the requirement forbids (design.md)
- [ ] 2.3 Do **not** pass `token_verification_enabled` — `AsyncApp` has no such parameter; it exists only on the synchronous `App`
- [ ] 2.4 Construct the app with `raise_error_for_unhandled_request=True` and register an `@app.error` handler returning `BoltResponse(status=200)` for `BoltUnhandledRequestError`, so an event with no specific handler is acknowledged instead of receiving Bolt's default 404. Not a catch-all listener: Bolt's unhandled-request path runs only after listener matching has failed, so it cannot shadow a real listener (design.md, Verified Finding 5)
- [ ] 2.4a In that handler, branch on `isinstance(error, BoltUnhandledRequestError)`; for every error that is not one, **log it and return nothing**, leaving the response as Bolt left it. Returning `BoltResponse(status=200)` unconditionally is wrong: harmless on the events path, but a genuine failure-into-success conversion on the slash-command and interactivity paths this helper is built to serve next (design.md, Verified Finding 5). `@app.error` receives *all* listener errors and displaces Bolt's default handler, whose contribution is the log; with `process_before_response` at its default an events listener's error arrives after the acknowledgement is already decided, so status is not the lever — the log is. A handler that returned silently for unrecognised errors would delete the only trace of a failed answer post (design.md, "This is done with `raise_error_for_unhandled_request=True`…")
- [ ] 2.5 Provide the FastAPI wiring helper over `slack_bolt.adapter.fastapi.async_handler.AsyncSlackRequestHandler`, so a module mounts its own app at its own path
- [ ] 2.6 Keep construction lazy behind a cached factory, **keyed on the app identity task 2.1 takes as a parameter** — not on the accessor or predicate objects, and not on the signing secret. Keying on a callable's identity means a caller passing a fresh closure per request never hits the cache and builds a new `AsyncApp` and `AsyncWebClient` every time, while every test still passes and this task's own import-time check stays green. Keying on the secret makes a rotating value the cache key. A single slot is equally wrong
- [ ] 2.6a Give the cached factory a reset seam. Task 7.8 exercises the same module under several environment states, and a warm cache would let it observe an app built from an earlier state — passing vacuously rather than proving anything, which is the silent-pass failure mode section 6 exists to prevent — `products` gets its own instance from its own variables, which is the helper's whole justification (proposal.md: "a lazily-built, per-app Bolt instance"). No `AsyncApp` at import time and none at startup (constrained by `test_main_slack_wiring.py`'s fresh-interpreter import guard, which is not modified)
- [ ] 2.7 Add **no** failure handling to the helper for an empty or malformed signing secret, and confirm why none is needed: `AsyncApp` does not raise for one (`async_app.py:217-222` defaults it to `""`), and Bolt's own `AsyncRequestVerification` then answers `401 {"error": "invalid request"}` natively (`request_verification.py:63-64`). An earlier draft specified a named-error contract here on the false premise that Bolt raises `BoltError`; that contract is withdrawn (design.md, "A request arriving while the signing secret is absent or empty")

## 7. New tests for this change's own requirements

- [ ] 7.1 An authentic `event_callback` whose event type has no handler receives a success status and does not invoke omni-agent (`slack-trigger`: "An Event With No Registered Handler Is Still Acknowledged")
- [ ] 7.2 Handling a signed `app_mention` with a fake token attempts **no** outbound Slack call other than the answer post — asserted by intercepting outbound HTTP, not by inspection. This is the test that would have caught the `auth.test` defect (`slack-trigger`: "Handling An Event Requires No Credential Verification Call To Slack")
- [ ] 7.3 Application startup makes no outbound Slack call
- [ ] 7.4 An authentic inbound request is verified and acknowledged while outbound Slack is unreachable
- [ ] 7.5 A bot-authored `app_mention` — carrying `bot_id`, or a bot-authored `subtype` — is acknowledged, invokes omni-agent zero times and posts nothing (`slack-trigger`: "Bot-Authored Events Do Not Trigger A Reply", scenario 1)
- [ ] 7.6 A person-authored `app_mention`, carrying neither, still receives its answer — so the 3.5 guard is not over-broad (same requirement, scenario 2)
- [ ] 7.7 A signed `app_mention` still reaches its own handler while unhandled-request acknowledgement is active (`slack-trigger`: "An Event With No Registered Handler Is Still Acknowledged", scenario 2)
- [ ] 7.8 Seven cases, each starting from a cold cache (task 2.6a) (`slack-trigger`: "A Request That Cannot Be Handled With Available Credentials Is Rejected"). None of the first four may yield 500 or an acknowledgement: signing secret **absent** → 401; signing secret **present but empty** → 401; bot token **absent**, on an `app_mention` → 401; bot token **present but empty**, on an `app_mention` → 401. Then three carve-outs, each with the **bot token absent**: a `url_verification` challenge → echoed, **not** 401 (also "Endpoint Responds to Slack's URL Verification Challenge"); an `event_callback` whose event type has no handler → acknowledged with a success status, **not** 401 (also "An Event With No Registered Handler Is Still Acknowledged"); and a **bot-authored `app_mention`** → acknowledged, **not** 401 (also "Bot-Authored Events Do Not Trigger A Reply"). The last two are what stop this requirement contradicting those two. They reach their outcomes by different routes — the secret's absence via the adapter's `KeyError` catch, its emptiness via Bolt's own request verification, the token's absence or emptiness via the `before_authorize` middleware — so each is asserted rather than inferred from another
- [ ] 7.9 With `SLACK_BOT_TOKEN` set in the environment, a signed `app_mention` makes no `auth.test` call — task 2.2a's guard holds and Bolt's fallback cannot silently reinstate single-team authorization (design.md, Verified Finding 7). Assert the guard's own response too, so the forbidden-environment behavior is pinned rather than emergent. Without this test the whole no-credential-call guarantee is green in a clean environment and false in one carrying that name
- [ ] 7.10 Two different workspace members' mentions are each processed the same way, with no consultation of sender identity (`slack-trigger`: "No Sender Identity Restriction (Deferred)", added second scenario)
- [ ] 7.11 A listener error that is **not** a `BoltUnhandledRequestError` is still logged by the `@app.error` handler. Assert on the **log record** — not on the HTTP status, which is already decided by the time the error arrives, and not on the posted failure message, which task 3.4's own `except` produces without the error ever reaching `@app.error`. Use a case that genuinely escapes the listener: the failure-message post itself failing, which is the scenario design.md argues from (task 2.4a)
