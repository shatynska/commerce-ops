## 1. Stop the runtime syncing

- [x] 1.1 Add `ENV UV_NO_SYNC=1` to the `Dockerfile`, **after the build-time `uv sync`** so a variable meant for the runtime cannot alter how the image is built. Instruction order relative to `HEALTHCHECK` is irrelevant — image environment is image configuration, and a healthcheck reads it either way (verified against a probe image whose `ENV` follows its `HEALTHCHECK`). Comment it with what it prevents: `uv run` re-syncs by default and its default group set includes `dev`, so without this the runtime undoes line 11's `--no-dev` and downloads test tooling into a running production container
- [x] 1.2 Leave `uv sync --frozen --no-dev` at build time exactly as it is. It was never the fault, and the change is only about what happens after the image is built
- [x] 1.3 Do **not** add `UV_FROZEN`. design.md records why: rewriting the lock requires `pyproject.toml` and `uv.lock` to disagree, which cannot happen inside an image whose build ran `uv sync --frozen` against both. A second variable guarding an unreachable state invites the belief that both are load-bearing

## 2. Take uv out of the healthcheck

- [x] 2.1 **Confirm the interpreter path against the built image** before using it: `docker run --rm <image> ls -l /app/.venv/bin/python`. A wrong path makes every `app` container permanently unhealthy — and `up -d --wait` has already replaced the previous working container by the time health is evaluated, so the failure is known only after the thing that worked is gone. `worker` disables its own healthcheck but waits on `app` being healthy, so it never starts either (design.md — Risks)
- [x] 2.2 Rewrite the `HEALTHCHECK` to call that interpreter directly instead of `uv run python`, keeping the probe's body, its intervals and its `|| exit 1` unchanged — only the launcher changes
- [x] 2.3 **Add** a comment explaining why this one call site bypasses uv (there is none today — `Dockerfile:13-14` is bare) while the `CMD` chain does not: it is a fixed string, so it has no operator-typed variant to miss, and it runs every 10 seconds for the life of every `app` container

## 3. Prove it in the pipeline

- [x] 3.1 Add a step to `.github/workflows/deploy.yml`'s **build job**, after the image is built and before the deploy job takes it: `docker run --rm --network none ${{ env.IMAGE_NAME }}:${{ github.sha }} sh -c 'uv run python -c "import commerce_ops.worker"'`, failing the job if it does not succeed. **It must go through `uv run`, in that operator-typed shape** — the launcher *is* the subject of the test. A check invoking `/app/.venv/bin/python` directly, which section 2 has just made the preferred launcher elsewhere, never invokes uv and so passes identically whether or not `UV_NO_SYNC` is set: a guard that cannot fail for the reason it exists. This is what makes the requirement's "the pipeline verifies this before deploying" scenario true, and it is what the design's standing-guard claim rests on — without it the property holds only until the next `Dockerfile`, base-image or `uv` change
- [x] 3.2 Make that step's failure stop the deploy rather than warn. The deploy job already `needs:` the build job, so a failing step there is sufficient — confirm that rather than assume it
- [x] 3.3 Have the step assert both halves, **both through `uv run`** for the reason in 3.1: the application imports (`import commerce_ops.worker`), and the dev group is absent (`uv run python -c "import pytest"` must fail). A container that starts offline because it silently skipped its work would pass the first assertion alone.

  **Run the negative half with the network available**, unlike the positive one. Inside `--network none`, `import pytest` fails because no index is reachable, so the assertion would pass identically whether or not the dev group would have been installed — a check that cannot detect what it names. With the network up, a failure means "not installed", which is the property scenario 2 states

## 4. Verify against a built image, locally

- [x] 4.1 Build the image locally
- [x] 4.2 **The acceptance check: `docker run --rm --network none <image> sh -c 'uv run python -c "import commerce_ops.worker"'` succeeds.** Removing the network is the test, not reading back the `ENV` — the fault being fixed was invisible to inspection, since the `Dockerfile` said `--no-dev` and the runtime ignored it. Note the `sh -c 'uv run …'` form deliberately: it exercises the operator-typed shape, which is the call site the whole `ENV`-over-flags decision turns on
- [x] 4.3 Confirm the dev group is absent at runtime: `docker run --rm <image> sh -c 'uv run python -c "import pytest"'` must **fail**. If it succeeds, something still installed it
- [x] 4.4 **Confirm starting a container installs nothing** (spec: "Starting a container installs nothing"). **Run this after 4.6**, not in list order: the second capture needs a container that has actually started its real `CMD`, and that chain runs `preflight && alembic upgrade head`, which needs a reachable Postgres that only 4.6 brings up. Capture `uv pip list --format=freeze` from a bare `docker run`, then the same via `docker compose exec app …` once the container reports healthy, and require the two to be identical. **Use `uv pip list`, not `python -m pip`** — a uv-created venv has no `pip` (verified: `No module named pip`), and not `uv run`, which is the thing under test on both sides. What this catches that 4.2 cannot: a start-time install served from the image's own uv cache, which needs no network and so is invisible to `--network none`
- [x] 4.5 Run the healthcheck command by hand against a running container and confirm it exits 0 while the app serves. Then confirm it exits non-zero when the app does **not** serve — produce that state by running the probe during the container's start window before uvicorn binds — which means **taking this observation while 4.6 is starting, from a second shell**, since `--wait` blocks the one that started it — **Prefer that method.** The alternative — freezing the server with `docker exec <container> sh -c 'kill -STOP 1'` (via `sh -c`, because Debian slim ships no `procps` and so no `kill` binary) — does not produce the observation this task wants: `Dockerfile:14`'s probe calls `urlopen` with no `timeout`, and task 2.2 keeps that body unchanged, so against a stopped PID 1 the listening socket still accepts from the backlog and a hand-run probe **blocks indefinitely rather than exiting non-zero**. The 3-second bound is Docker's `--timeout`, which applies only when Docker runs the probe — so if the freeze method is used at all, read the result from `docker inspect --format '{{json .State.Health}}'`, never from the hand-run command's exit code. Do **not** try to kill uvicorn either: `Dockerfile:40` execs it as PID 1, so terminating it stops the container instead of leaving an unhealthy one to probe. A probe that cannot report unhealthy is worse than no probe
- [x] 4.6 Bring the full stack up with `docker compose up -d --wait` and confirm it returns 0 with `app` healthy, matching what the host runs. **Three prerequisites the compose file does not provide locally**, each of which aborts the command before anything starts: `docker network create platform_edge` (it is declared `external: true`, so compose will not create it), a local `.env` carrying `POSTGRES_PASSWORD` and `IMAGE_TAG`, and tagging 4.1's build as `ghcr.io/shatynska/commerce-ops:$IMAGE_TAG` so the stack resolves the image just built rather than pulling another. Do **not** edit `docker-compose.yml` to work around any of these — testing a modified file would defeat this task's whole purpose, which is to exercise the file the host runs. Remove the `.env` afterwards: `Settings` reads it, so leaving it in place changes what the unit tests see
- [x] 4.7 Confirm the worker's first log line (`scheduled-work worker starting; N schedule(s) registered`) arrives within seconds rather than after a download, and that no `Downloading`/`Installed` lines precede it
