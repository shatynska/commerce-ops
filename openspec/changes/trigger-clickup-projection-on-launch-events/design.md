## Context

See `proposal.md` — Why, for the motivation. Two facts from the codebase shape this design rather than the proposal:

- `converge_launch` (`clickup_sync.py:553`) requires a working `read_product: ProductReader` (no default — unlike `roster`, which defaults to `None`) because a launch's list is named from the catalog product's name and SKU. It has exactly one caller today: `clickup_sync_job.py`'s periodic pass, running in the **worker process**, where `worker.py` injects `read_product`/`read_people` into that module's globals after `register_all()` — deliberately, because `.importlinter`'s `products-infrastructure-boundary` bars `launch.infrastructure` from constructing catalog's store, and only a composition root outside that boundary may supply the reader.
- The three trigger points this change adds an eager call after — `start_launch` (`slack_entry.py`), the gate-confirmation decision path (`gate_confirmation.py`), and the webhook's `advance_and_ask` (`clickup_webhook.py`, dispatched via `BackgroundTasks`) — all execute inside the **HTTP process** (`main.py`'s FastAPI app), not the worker. `main.py` currently wires a request-scoped roster reader (`_RosterReader`) and a request-scoped catalog reader (`_RequestScopedCatalog`, already used by the tracking and product-dossier pages) into that process, but deliberately declined to give `gate_confirmation` a catalog reader there — its own comment reads "No catalog reader here, deliberately: this process answers decisions, and only the *ask* names the product. The worker composes those, so the reader is injected there." That reasoning was scoped to what `gate_confirmation`'s decision path alone needed; it does not extend to this change, which adds a second concern — eager convergence — to the same process, and that concern does need product data.
- `gate_progression_job.py`'s own periodic pass also crosses gates (it is one of the three `progress_launch` call sites), and it runs in the worker process, where the readers already exist for `clickup_sync_job` but are not currently shared with `gate_progression_job`.
- `scheduled-jobs` forbids only an *externally reachable* interface for starting recurring work, and separately, `register_scheduled`'s cron registration has a real technical floor around ten minutes (`gate_progression_job.py`'s own comment: `*/5` exceeds the 60,000-occurrence-over-400-days cap `scheduled-jobs`' longest-gap computation enforces; `*/10` does not). Neither constraint blocks a direct, in-process function call dispatched immediately — which is what `advance_and_ask` already does today, and what this change extends with a second cascade.
- `slack_entry.py` and `gate_confirmation.py` register **Slack Bolt listeners** (`@app.command`/`@app.view`/`@app.action`), not FastAPI routes — they have no `BackgroundTasks` parameter, and it does not apply to them. `clickup_webhook.py` is the only genuine FastAPI route among the three HTTP-process call sites; it is also the only one that already uses `BackgroundTasks` (for `advance_and_ask`). Bolt's `AsyncApp` is built with `process_before_response` left at its `False` default (`slack_app.py`), which is what already lets `gate_confirmation.py` call `ack()` and then keep running — including its own `post_gate_ask` dispatch — without blocking Slack's response; that is the mechanism the two Bolt listeners have available, not `BackgroundTasks`.
- `clickup_sync_job.py`'s periodic pass opens **one** `session()` for its entire run — playbook read, Custom Field configuration read, and the walk over every active launch all share it — and calls `converge_launch` per launch inside that shared session, inside a per-launch `try`/`except` for containment. It never calls `hold_launch_advance_lock`, and `hold_launch_advance_lock` requires a `transaction()` (its `pg_advisory_xact_lock` is transaction-scoped, per its own docstring). This differs from `gate_progression_job.py`'s `_advance_one`, which gives each launch its own `transaction()` and takes the lock inside it. An advisory lock only serializes callers that both attempt to take it — a caller that never takes it races a lock-holding caller exactly as if the lock did not exist.

## Goals / Non-Goals

**Goals:**
- Give the HTTP process its own means to call `converge_launch` for one launch, without changing where `converge_launch` itself runs from conceptually (same function, same collaborators, same idempotent convergence).
- Reuse `advance_and_ask`'s already-established shape (background dispatch, self-contained failure handling, post-commit timing) rather than inventing a new dispatch mechanism.
- Keep `clickup_sync_job`'s periodic pass, its cadence, and its role as the fallback, completely unchanged.

**Non-Goals:**
- Building any new scheduling, queueing, or notification infrastructure (a Postgres-backed signal table, `LISTEN`/`NOTIFY`, a tighter cron job). Considered and rejected below.
- Touching `reconcile_launch`, the webhook's completion recording, or any reconciliation/read-back behavior.
- Fixing `LaunchRepository.save`'s whole-aggregate-clobber defect (`docs/deferred-work.md`) — unaffected, since `converge_launch` never calls `LaunchRepository.save`.
- Shortening `clickup_sync_job`'s or `gate_progression_job`'s cron cadence.

## Decisions

**The HTTP process gets its own request-scoped `ProductReader`, mirroring `_RequestScopedCatalog` and `_RosterReader`, rather than reaching into the worker's injected globals.** The two processes are separate composition roots by design (`worker.py`'s and `main.py`'s own docstrings both say so); sharing a Python-level global across process boundaries isn't possible in any case. `main.py` already builds exactly this shape of reader for other launch-driving adapters (`launch_tracking_admin.catalog`, `launch_product_dossier.catalog`), so this is an extension of an established pattern, not a new one. The comment near `launch_gate_confirmation.read_people = _RosterReader()` needs updating to stop asserting "no catalog reader here" once this reader is added for the eager-convergence use.

**A single shared helper wraps `converge_launch` with its own error containment**, placed alongside `converge_launch` (or as a thin driving-adapter function analogous to `advance_and_ask`) and used by all four call sites — `start_launch`, the decision path, the webhook's `advance_and_ask`, and `gate_progression_job`'s own advance. It catches and logs any failure internally and never raises, exactly as `advance_and_ask` is already documented as doing ("`advance_and_ask` already catches its own failures"). This is what makes *A failed eager run does not fail the action that triggered it* (spec) hold structurally rather than by convention at each of the four call sites.

**Stand-down is inherited from each call site's own existing readiness check, not re-implemented.** All four callers already refuse to act while the served playbook cannot hold a launch, for reasons unrelated to this change: `start_launch` and `progress_launch` (all three of its call sites, including `gate_progression_job`'s own pass) already raise or stand down on `PlaybookNotReadyError` before this change exists to add anything after them. The eager helper is only ever reached once its caller has already cleared that check, so it never needs its own stand-down logic — it inherits the condition rather than testing it a second time.

**Dispatch differs by call site, matching the integration mechanism each one actually has:**
- `clickup_webhook.py` (a genuine FastAPI route) dispatches the helper via `BackgroundTasks`, after the triggering transaction commits — identical to how it already dispatches `advance_and_ask`. A slow ClickUp write must never delay the webhook's acknowledgement, for the same reason `advance_and_ask`'s own docstring gives for the ask it posts outside the lock.
- `slack_entry.py` and `gate_confirmation.py` (Bolt listeners, not FastAPI routes) have no `BackgroundTasks` to dispatch through. They call the helper by awaiting it directly after `ack()` — the same post-ack, non-blocking continuation `gate_confirmation.py` already relies on for `post_gate_ask`, made possible by Bolt's `process_before_response=False` default. This is not a weaker guarantee than backgrounding: Slack has already received its acknowledgement by the time the helper runs, exactly as `BackgroundTasks` achieves for an HTTP response.
- `gate_progression_job.py`'s periodic pass awaits the helper inline, per launch, inside the same per-launch loop it already runs `progress_launch` and `post_gate_ask` in — nothing in that context is waiting on a fast response, so there's no reason to background it there, and doing so inline keeps its own failure containment consistent with how that pass already contains `progress_launch` failures per launch. `gate_progression_job.py` needs its own `read_product`/`read_people` injected by `worker.py`, mirroring `clickup_sync_job`'s existing injection (the same reader instances can be reused across both worker-resident modules).

**No new scheduling or signaling infrastructure.** A Postgres-backed "pending eager convergence" table plus a very-frequent worker job, or a `LISTEN`/`NOTIFY` channel, were both considered as ways to keep `converge_launch` exclusively worker-resident. Rejected: `register_scheduled`'s ~10-minute cron floor would cap that path at the same latency this change exists to beat, and either mechanism is materially more new infrastructure than giving the HTTP process a reader it can already build from patterns already in `main.py`. A direct, backgrounded function call is also exactly what `advance-gates-from-clickup-webhook` already established as the precedent for "run this sooner than the pass" work.

**Concurrent convergence of the same launch is handled by relying on `converge_launch`'s existing idempotence for every case except first-time list creation, which is the one place a genuine race exists.** An eager call and the periodic pass (or two eager calls — e.g., a webhook-triggered one and a Slack-decision one racing the same gate crossing) both check-then-act against ClickUp and the mapping store; for an already-recorded list this is safe by the existing spec's own guarantees ("A launch whose recorded list still exists SHALL NOT get a second one"). But a launch's *first* list has no recorded mapping yet for either concurrent caller to check against, so two callers reaching `_ensure_list` at once for a brand-new launch could each decide no list exists and create one.

Taking the lock only on the eager side is not a mitigation: `clickup_sync_job.py`'s pass never takes `hold_launch_advance_lock`, and a lock only serializes callers that both attempt to acquire it — an eager call and the untouched pass would still race exactly as if neither took a lock. Closing the race for real means both sides taking it.

**The lock acquisition and `converge_launch`'s own writes deliberately do not share a transaction — a departure from every existing `hold_launch_advance_lock`/advisory-lock consumer in this codebase, not only `gate_progression_job.py`'s `_advance_one`.** `_advance_one`, `gate_confirmation.py`'s `_advance_after_approval`, and `launch_thread_lock.py`'s callers all bind the guarded repository writes to the *same* session that holds the lock; `launch_advisory_lock.py`'s own module docstring ("taken inside `transaction()` it is held for the whole cascade") states that same-session convention as the pattern's whole point. This change's two new call sites are the first to split the two. `_advance_one`'s shape is not the right one to copy wholesale here regardless: it rebinds `LaunchRepository` to the lock's own session, so a mid-cascade failure rolls every crossing back — and `launch-gate-progression`'s own spec text explains why that is *right* there and *wrong* here: "This is deliberately unlike `launch-clickup-sync`'s rule that work completed for a launch before its failure stands... An atomic unit is worth more than a partially-advanced launch nobody chose" for a gate crossing, because it is a cheap local write the next pass redoes for free. A `converge_launch` call is the opposite: many ClickUp requests against a rate budget, and `launch-clickup-sync`'s own requirement ("One launch's failure does not stop the other launches being converged") already guarantees, with a tested scenario, that "work completed for a launch before its failure SHALL stand." `ClickUpMappingRepository`'s writes each call `commit()` internally, and `transaction()`'s `join_transaction_mode="create_savepoint"` turns every such inner commit into a savepoint that the *outer* transaction's own rollback can undo — so if `converge_launch`'s collaborators (`mapping` above all) were rebound to the new lock-holding transaction, a mid-launch failure would silently reverse that guarantee, undoing list and task creation that had already succeeded against ClickUp, and reopening the very race this fix exists to close on the launch's next attempt.

So `clickup_sync_job.py`'s per-launch loop opens a `transaction()` **only to acquire the lock** — `hold_launch_advance_lock(lock_session, launch.product_id)` — and calls `converge_launch` from inside that `async with` block using the pass's *existing* `mapping`, `clickup`, `read_product` and `roster` collaborators, still bound to the pass's own outer `session()`, exactly as today. Nothing about `transaction()`'s savepoint machinery applies to writes made through a different session on a different connection, so `converge_launch`'s commits behave exactly as they do today — partial progress on failure survives, unchanged. Because the call is a single sequential `await` with no concurrent interleaving inside that coroutine, the writes still happen strictly between the lock's acquisition and its release in real time: mutual exclusion against a concurrently-locking caller (the eager path, which follows the same shape — lock first, then call `converge_launch` through its own already-existing collaborators) holds exactly as it would if the two shared a transaction, without adopting `_advance_one`'s rollback-everything semantics. The eager helper (task 1.1) is built the same way for the same reason: its `transaction()` holds the lock only; `converge_launch`'s own collaborators are never rebound to it.

This narrows, but does not eliminate, the earlier proposal's claim that `clickup_sync_job` is unchanged: its cadence, its role as the fallback, its reconciliation behavior, its own containment and stand-down rules, and — now stated explicitly — its partial-progress-survival guarantee are all unchanged; only the addition of a lock acquisition around its existing `converge_launch` call changes, and only to close this race. `proposal.md`'s non-goals are revised to say so precisely rather than claim no change at all.

One ordering question this section resolves rather than leaving implicit: in `gate_confirmation.py`'s decision path, the eager helper is awaited *after* `respond(message)` sends the decider their reply — the decider is told what their decision did (the gate opened or didn't) without waiting on ClickUp latency, consistent with *A decision records the approval and reports what it did*'s existing requirement that the reply is not held up by work still in flight.

## Risks / Trade-offs

- **New ClickUp call volume from the HTTP process's request-handling paths, even backgrounded, adds pressure to the same rate-limited API that motivated widening `clickup_sync_job`'s cadence today** → Mitigated by `retry-clickup-rate-limits`'s existing bounded backoff on the shared ClickUp client, which every `converge_launch` call already goes through regardless of caller, and by the fact that each eager call converges exactly one launch, not the full active set the periodic pass sweeps.
- **Extending the HTTP process's catalog access, where a comment currently states none is needed** → Mitigated by reusing the exact reader pattern (`_RequestScopedCatalog`) already sanctioned in `main.py` for other reads, and by the import-linter boundary itself being unaffected — the launch module still never constructs catalog's store directly.
- **Holding an advisory lock around a ClickUp network call is a longer lock hold than the existing gate-crossing paths take** (`gate_progression_job.py`'s own docstring: "the ask is posted outside the lock" specifically to avoid holding a launch against a slow delivery), and this now applies on **both** sides — the eager helper and `clickup_sync_job.py`'s own per-launch `converge_launch` call — not just the eager path → Accepted for now, since `converge_launch`'s writes are bounded by `retry-clickup-rate-limits`'s own backoff ceiling rather than unbounded, and the lock is per-product, so it only serializes concurrent work on the *same* launch: the pass still converges other launches in the same run without waiting on one launch's lock, and it only contends with an eager call for that same launch, which is rare. Worth revisiting if the backoff ceiling turns out to make this lock hold long enough to matter in practice.
- **`clickup_sync_job.py`'s per-launch loop changes shape** (its `converge_launch` call moves from the pass's shared outer session into its own `transaction()`) even though the proposal frames this change as adding a fast path without touching the pass → Mitigated by scoping the change precisely: only the transaction/lock wrapping of one call changes; cadence, fallback role, containment, and reconciliation behavior do not. `proposal.md` states this narrowed non-goal explicitly rather than the stronger "completely unchanged" claim the first draft made.

## Migration Plan

No schema changes, no new tables, no feature flag. The periodic pass is untouched and keeps self-healing anything the eager path misses, so this ships as an ordinary PR through the existing deploy path (`AGENTS.md`'s "every change reaches the server through a pull request") with no special rollout sequencing. Rollback is a plain revert; nothing about the eager path is load-bearing for correctness, only for latency.
